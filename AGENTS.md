# AGENTS.md

Project authority for `adversarial-review-loop`. Read this before changing anything here.

For **how to review** a change to this repo, use the `adversarial-review` skill in `.agents/skills/` — it owns the review procedure and the full invariant checklist. This file owns what the project *is* and the rules a change must not break.

## What this is

A Claude Code plugin that turns an external adversarial review into an **enforcement gate** on `git commit`. Claude implements a plan phase by phase; each phase's commit is intercepted by a `PreToolUse` hook, the whole working state is snapshotted into a git tree, the reviewer reviews the delta, and the commit proceeds only if the review passes.

It is a security-shaped component. The failure that matters is not a crash — it is an **unreviewed commit that looks reviewed**.

## The five rules

Everything else is detail. These are not negotiable, and a change that weakens one is a defect even if every test passes.

0. **A gate that cannot prove it is running denies.** The hooks register at plugin load (`hooks/hooks.json`), not on skill invocation, so the dispatcher runs in every Claude Code process the plugin is enabled in — including a fresh `claude --resume` of a session that armed the loop yesterday. Skill-scoped hooks were the original design and they had a hole exactly there: a resumed process registers no skill hooks, `state.json` still says `ACTIVE`, and every commit lands ungated (measured 2026-08-30, see `tests/STEP0.md`). A session pointer binds a session to its activation; a hook call with no pointer is a session that never *completed* `implement`/`resume`. Three things still deny there, checked in this order. (a) The session **asked**: `commands/intent.py` runs on `UserPromptSubmit` and records a marker when the prompt *is* an arming command, before the skill expands — because a failed expansion gives Claude no turn, so nothing the skill body says ever reaches it. `intent` mints a token and `pointer_write` publishes the pointer **carrying that token** before best-effort unlinking, so the check is the token, not the file: a marker the pointer names is answered (a crash between the two leaves litter, not a wedge), while unlinking first would have opened a window with no marker, no pointer and no `latest` in which a saved `ACTIVE` activation went ungated. **The marker's write order is not guaranteed** — measured live, it can land *after* the expansion it announces has already run — so a marker whose worktree has a live gating activation (`ACTIVE`/`ARMED`/`RECONCILE`) bound to the same session is also answered (`hooks._answered_by_live_activation`), never recorded as a failure: the gate is on in both possible histories. An *unanswered* marker means no `arm` has answered since — which is why `hooks.pending_intent` is checked *ahead of* the pointer (a `DISARMED`/`COMPLETE` pointer from an earlier activation must not hide a failed re-arm) and scoped to the worktree the marker names (a failed arm in repository A is neither enforced against nor consumed by a call in repository B). Then `hooks.record_unstarted_arm` records `ARM_FAILED` and denies, exactly as the skill-hook design did. (b) The repository this call is about **cannot be resolved**: `paths.repo_root_or_raise` distinguishes git answering "not a repository" from git not being runnable, a vanished `cwd`, a timeout — the first is a pass, the rest deny, because "nothing to enforce" has to be proven. This holds for *bound* sessions too: `hooks.resolve_repo` raises on the same conditions, and `pretool` denies, `gate-stop` blocks and `confirm-commit` reports "NOT confirmed" rather than reading "could not tell" as "another repository" — which, from a subdirectory of the armed worktree with git off the hook's PATH, would pass a commit run through `/usr/bin/git`. The marker read is three-state for the same reason: absent is "no intent"; unreadable, unscopable or token-less is neither — it denies **everywhere** without being recorded against, or consumed by, whatever repository the call is in, and only `deactivate --session` (the user's `/adversarial-review-loop:stop`) discards it. Consuming it locally would hand repository A's request to repository B and leave A ungated. (c) The worktree's `latest` activation is **still live**: this session is *unbound*, and `hooks.unbound_activation` denies every mutation until `resume` binds it, without touching the other session's document. Everything else — every unrelated session in every unarmed repository — passes silently and writes nothing. Absence of state is never an opt-out; absence of *this session's* state in an armed worktree, or after an arming prompt, is a denial. This is why `deactivate` leaves the session pointer in place and relies on `DISARMED` instead of deleting it.
1. **Nothing converts a failure into an approval.** Missing state, malformed JSON, a snapshot failure, a timeout, a non-zero reviewer exit, empty output, absent markers, an unknown verdict, an evidence ceiling — every one of them blocks or escalates. Operational uncertainty is never "no findings".
2. **Hook stdout is protocol.** Hook entrypoints (`pretool`, `confirm-commit`, `posttool-failure`, `gate-stop`) emit valid Claude hook JSON or nothing. Diagnostics go to stderr only, through `arl.util.log`. A stray `print` in a module that runs under a hook corrupts the response — `report.store` is deliberately silent on stdout for this reason. An uncaught exception at the top level still emits that event's fallback JSON before exiting 0; see "Interpreter invocation" below for the full contract.
3. **Nothing is written inside the repository under review, with one explicit exception.** All state, frozen plans, bundles and reports live under `$XDG_STATE_HOME/adversarial-review-loop/`. The snapshot uses a throwaway `GIT_INDEX_FILE` and never touches the real index or worktree. `sys.pycache_prefix` keeps `__pycache__` out of both the plugin repo and the reviewed one; see "Interpreter invocation" below. The exception is `config <key> <value> --repo`, which writes the repository's own `.adversarial-review-loop.json` — user-only, explicit, documented in the README, and never triggered by a hook or reachable from Claude. No code path that runs on a tool call ever writes inside the reviewed repository.
4. **The user owns the exits.** `implement`, `finish`, `stop`, `resume`, `config`, `accept` and `pause` are `disable-model-invocation: true`, and Claude's own route to `finish`, `deactivate` (the escape `stop` runs), `resume`, `config`, `accept` and `pause` — Bash — is denied in `commands/pretool.py`. `pause` is here because it decides whether the Stop gate keeps asking for the remaining phases: reachable by Claude it would be an unbounded, strictly better `defer`, and `defer` is bounded by `max_defers` precisely because "stop asking me for more" is also the shape of an agent that has stopped making progress. `accept` is the one of these that grants something rather than only ending or adjusting the activation — see `commands/accept.py` for why binding it to one exact tree hash is what keeps it from being able to pre-approve anything else. See below for what Rule 4 does and does not guarantee.

### What Rule 4 does and does not guarantee

The denial reads `tool_input.command` as a string, so it stops the direct route and nothing more. Two things defeat it, both confirmed by experiment:

- **A wrapper.** `bash escape.sh`, where the script commits and then runs `arl.sh deactivate`, is recognised as neither a commit nor an escape. The commit lands unreviewed and the mode ends.
- **Editing the state.** `status: DISARMED` written straight into `state.json` ends the mode with no command to inspect at all. The `PreToolUse` gate now refuses an *editing tool* aimed at the state root, but a shell command can still write the same file — the gate runs as the same user, and by the time it is asked about a command, that command is about to run.

**So Rule 4 is not enforceable against a deliberately adversarial model.** It holds against mistakes, drift, and a model following the loop's instructions, which is what the component is for. No file-based mechanism can do better: any token this plugin writes to disk, the model's shell can write too.

What *is* enforceable is reporting. `confirm-commit` reports a HEAD whose tree no review approved, and the Stop gate repeats it through `systemMessage`. The value of that second channel rests on `systemMessage` reaching the *user*, so that relaying it is not the model's decision — **that is assumed, not verified**, and it is `tests/STEP0.md` item 12. If it turns out to be model-visible only, this paragraph is wrong and the escape has no reliable reader at all. Closing the rule properly needs a host-only signal that a real user typed the slash command: item 11. Until both are settled, the limit stands as documented rather than fixed.

## The deny-list is still the security boundary

`scripts/arl/cmdshape.py` decides whether a commit command may run, and since the bashlex vendoring it does so with a real bash parser rather than a hand-rolled tokenizer. That change does **not** move the security boundary, and the reason is worth stating plainly, because it is not visible from a diff:

**The gate is still a parser that must agree with a parser it does not control.** It reads `tool_input.command` as a string and decides; Claude Code then executes that same string through a real bash. bashlex parses the *whole* shell grammar, so on its own it would happily hand back a clean AST for a pipeline, a subshell or a redirection — the gate would then have to decide, node by node, which constructs cannot reach the filesystem after the snapshot. That is the same policy question as before, re-expressed against a grammar large enough to hide a mistake in.

**`_deny_shell_grammar` runs first and is unchanged in substance from `cmdshape.sh`.** `$`, backticks, `;`, `|`, `<`, `>`, `(`, `)`, `{`, `}`, unquoted globs, a bare `&`, newlines and comments are all refused before bashlex ever sees the command. What survives is the same tiny language as before — words, two quoting forms, backslash escape, and `&&` — and *that* is what bashlex now turns into words (`tokenize` in `cmdshape.py`).

**What the parser bought is word-splitting and quote handling, not a wider grammar.** Splitting, quote removal and backslash handling are now bash's own rules as bashlex implements them, not as re-derived by a loop of this repository's own — and a command bashlex cannot parse (a trailing unescaped backslash, an unterminated quote) is refused rather than tokenized on a guess, which the hand-rolled version sometimes did.

**Therefore: the deny-list and the parser are still a single design, and relaxing the deny-list without re-reading `_words` is the specific change that breaks this component.** If you want to accept any construct currently rejected up front — command substitution, redirection, process substitution, a pipeline, ANSI-C quoting — the parser can now represent it, but deciding it is *safe* to accept is a separate change with its own evidence. Widening `_deny_shell_grammar`'s accepted character set is not a small change, however small the diff looks.

**`unresolved_expansion` is a different check with a narrower guarantee, and it is not the boundary.** It runs on *every* `Bash` call rather than only the commit path, before anything is classified, and it exists for one reason: textual detection must not go blind on a command **name**. `$(printf git) commit` runs `git commit` and contains no `git` for `_COMMIT_RE` to match, so a name an expansion decides is refused outright. It is scoped to exactly that. An expansion in an *argument* is allowed (`echo "exit=$?"` runs `echo`), and so is anything inside a heredoc body whose delimiter is quoted, which bash does not expand at all — refusing those bought no part of the guarantee and cost a measured run roughly six scratchpad files and a second `Bash` call each. Two things beyond the name are still refused: an *unquoted* heredoc body, which bash does expand and which bashlex files under a `heredoc` node where the name-only rule would never see it, and an argument to a known exec wrapper (`sh -c "$CMD"`). **That wrapper list is a speed bump, not a boundary** — `python3 -c "$CODE"` walks straight through it, as `python3 script.py` always did. What actually catches a commit made that way is `confirm-commit`.

**The deny-list did not move when that check narrowed.** On the commit path `$`, backticks, `;`, `|`, redirection, subshells, globs and newlines are all still refused, so `git commit -m "$(x)"` is denied exactly as before — by `validate_commit`, not by the pre-check. A heredoc whose body contains the words `git commit` is still detected (`_COMMIT_RE` reads the raw text multiline) and still refused as a commit shape. Over-detection stays the safe direction.

**The one invariant `unresolved_expansion`'s textual scan must never break: it may not skip text bash executes.** The only thing it skips is a heredoc body, so every rule in it is there to stop a `<<` being read as a heredoc where bash does not read it as one, or as one ending later than bash ends it — a `<<` inside a comment, a `\`-newline line continuation (in the command text *and* inside the delimiter word), a left shift inside `(( ))`, and a delimiter word read with bash's exact quote removal. Each of those was a real bypass, each found by differential testing against bash rather than by reading. **If you touch that scanner, re-run that differential** (`tests/unit/test_cmdshape.py` carries the cases; the property is "bash executed it and the gate returned no denial"), because a mis-skip there is silent and hands over an ungated `git commit`.

Two things make this defence in depth rather than a single point of failure. **They are not equally load-bearing, and only the first is unconditional:**

- **`confirm-commit` looks after every commit-shaped call, always — but it makes two different guarantees, and they must not be run together.**
    - *The approved path*, `_verify`: reached only when a pending approval exists **and** the command matches the one that was approved. It checks `HEAD^{tree} == pending_approved_tree`, that the parent is the commit HEAD was at when the review passed, and that the worktree is clean afterwards. This is the strong check, and it is what advances a phase.
    - *The bypass path*, `_guard_unreviewed_head`: reached when there is no pending approval, or the command was not recognised as the approved one — which is exactly the shape a parser bypass produces. It asks **one** question: is `HEAD^{tree}` in `approved_trees`? If yes it returns silently. It does not bind against `pending_approved_tree`, does not check the parent, does not check cleanliness, and does not ask whether *this* command produced that commit.

  **State the guarantee at its real width: a bypass whose HEAD tree is absent from `approved_trees` is detected and reported, and no config key can suppress that.** Two things fall outside it and must not be papered over. A bypass that lands a tree already in the set is not reported at all — an approved commit that *failed* still leaves its tree cached, so a later wrapper can build an arbitrary commit on that tree, with any parent, and pass silently. And membership in `approved_trees` is not evidence a model read anything: the baseline tree is in it, and so is any tree where `ignore_globs` matched everything. History rewrites onto an approved tree are outside this defence.

  What is *additionally* status-dependent is the remedy: `RECONCILE` is written only for a status in `_RECONCILABLE`. For one in `_REPORT_ONLY` (`posttool.py:221` — `DISARMED`, `COMPLETE`, `NEEDS_HUMAN`, `STALE`, `RESUMED`) the hook reports and writes nothing, since those activations must not be reopened. That is reachable by config: `confirm-commit` reloads configuration at bind time, so lowering `ttl_hours` between the gate and the commit makes the activation `STALE` and the bad commit is reported rather than reconciled. Preserve the detection; do not describe the recovery as unconditional.
- **The final cumulative review at the Stop gate, only when `final_review` is on — and it is off by default.** It covers the end state regardless of what happened per commit, which is the strictly stronger claim, but the *automatic* one is opt-in. On a default install, the Stop path's protection is the deny-list plus `confirm-commit` and nothing else. Do not write, or rely on, "the cumulative review will catch it": say which configuration you mean. `finish` is the other route to the same review and it ignores `final_review` entirely — but only that key. It is still subject to the ordinary finishability checks (`_refuse_unless_finishable`), which are themselves config-reachable: a `ttl_hours` low enough to make the activation `STALE` refuses `finish` before any review runs. And once an activation is `COMPLETE`, both routes are closed permanently.

A parser failure mode unique to bashlex: a command it cannot parse, or hangs on, must deny — never fall through to an approval. `CommandShapeTimeout` and the `signal.setitimer` deadline in `cmdshape.py` exist for exactly this; see "Interpreter invocation" below.

### The argument channel is not escaped

`skills/implement/SKILL.md` passes `--args "$ARGUMENTS"`. Claude Code substitutes `$ARGUMENTS` textually, without shell escaping, and the body runs through `eval`. A plan path of `x"; id; echo "` therefore executes `id`. This is confirmed, not theoretical.

No change to the body fixes it — double quotes are broken by `"`, single quotes by `'`, and the substitution precedes any shell. The containment is `disable-model-invocation: true` on the skill, which means only the user can supply the path. **Do not remove that flag**, and do not add a second interpolated argument without re-reading this. `commands/arm.py`'s character-set check is still worth keeping, but understand what it does and does not do: it runs after any injected command has already executed, so it protects the loop's state, not the machine.

## Resume: a second arming path

`resume` continues an existing activation rather than starting one — across a new session (the ordinary case) or in the current one (to change `--until`, the model, or the plan without a new session). It shares helpers with `arm.py` (`_ArmFailure`, `_resolve_plan`, `_check_reviewer`, the flag parser) but lives in its own module, `commands/resume.py`, because the invariants below are specific to it.

**Neither `skills/implement/SKILL.md` nor `skills/resume/SKILL.md` carries a `hooks:` block, and neither may grow one.** Every hook lives in `hooks/hooks.json` and registers at plugin load — see "Plugin-level hooks, 2026-08-30" in `tests/STEP0.md`. Skill hooks register on invocation, per process, and were the reason a resumed session could commit ungated while `state.json` claimed enforcement; adding one back would also fire the gate twice per tool call in the process that invoked the skill. If a skill ever needs an extra hook, it goes into `hooks/hooks.json` for every session.

### One live activation per worktree

Two activations gating the same worktree independently — each with its own pointer, each approving commits against its own approval set — is the failure every rule below exists to rule out.

**Cross-session resume retires the predecessor before the successor exists, never the reverse.** Retirement writes `status: "RESUMED"` under the predecessor's own lock; only after that succeeds is the successor's directory materialised, its document written, and the pointers repointed. This is the fail-closed order: if the process dies in between, the predecessor is `RESUMED` (denying) and the successor has no state at all (denying, per Rule 0) — both sides deny, **there is no automatic rollback**, and the recovery is `implement`. The reverse order — successor first, predecessor retired second — would leave a real window with two simultaneously `ACTIVE` activations over one worktree.

**A retirement must never span an in-flight approval.** `pretool` sets `pending_approved_tree` under the same lock a retirement takes, so the two serialise: whichever wins, the other observes a consistent world. Skip this and a `pretool` approval can land against the predecessor moments before it is retired, and `confirm-commit` then verifies that commit against the now-retired document. `_advance`'s `status="ACTIVE"` write is what makes this dangerous rather than merely stale: it would resurrect a blocking `RESUMED` activation back into a second live one. `_advance` is kept off `RESUMED` documents two ways — `_REPORT_ONLY` rather than `_RECONCILABLE` keeps `posttool._reconcile` off it, and retirement itself refuses to happen across a pending approval — because a `status="ACTIVE"` write from *any* code path is the resurrection mechanism, not just this one, and both guards exist for exactly that reason.

**A retired activation's directory is never mutated — with one bounded exception.** Every later revision, every later report is written into the *successor's* directory, copied byte for byte from the predecessor at retirement time. Editing anything in a retired directory would corrupt evidence a completed review was already run against, and reports already stored there still name it. The exception: a `reviewer.execute` **already in flight** when retirement lands. A review holds no lock across its (minutes-long) run by design, so `build_bundle` and `invoke` may already have written `bundles/<seq>/` and `raw/<seq>-*` into what is now the retired directory, and those cannot be unwound. Everything `execute` still controls at that point *is* withheld: the `state.json` fingerprint guard (`hooks.Activation`, checked under the lock in every no-write path), and `_publish` writing the stored report **and** the `round_history` entry inside one such guarded transaction — one publication, so a retirement lands wholly before it (neither is written) or wholly after it (the successor copies both), never between the two. The stranded `bundles/`/`raw/` files are this-review-only and additive — no successor code path ever reads them, since the successor rebuilds its own bundle — so they are litter, not corruption. Closing even that needs retirement to fence in-flight reviews (there is no signal one is running today); it is a change to the retirement path, not to `execute`. A `clarify` in flight is the same shape: it may strand a `context/<n>-question.txt` and a `raw/<n>-clarify.out`, and it withholds the reply itself — its post-invoke `hooks.Activation` recheck refuses `_MOVED_DURING_RUN` rather than printing a clarification the activation no longer owns.

### The inverted carry-forward rule

The successor's document is built by copying the whole predecessor document and then resetting a *named* set of fields — never by enumerating what to keep. Enumerating what to keep is how a future field gets silently dropped the day it is added to `new_state_document` and this reset table is not updated to match. It already has one concrete failure mode on record: an explicit keep-list drops `report_seq`, and `reviewer.py` claims the next sequence from state and `shutil.rmtree`s the bundle directory for that sequence — a reset `report_seq` would have the first post-resume review overwrite the copied `001` report and destroy its bundle rather than continuing the sequence.

### `state.json` is not a trust boundary — treat everything read out of it that way

This applies to every field this feature added. A `plan_revisions[*].file` is a filename read out of state and then used to open a file: validate it with `paths.is_safe_component`, resolve it under the activation directory with `os.path.realpath` on both sides (a symlink planted in the activation directory must not redirect the read), and verify its recorded `sha256` before its content is used for anything — including showing it to the reviewer. A missing file, a failed containment check, or a hash mismatch is `NEEDS_HUMAN`, never a skipped attachment and never a silent fallback to `plan.frozen.md`. The same caution applies to `resumed_into`, `abandoned_pending_tree` and `abandoned_pending_head`: read for display or comparison, never trusted on their own to authorize a write.

### `STATE_VERSION` and legacy activations

Activations written before this feature exist on disk with none of the fields it needs — and they are exactly the ones a user wants to resume. Most missing fields degrade safely on their own (`State.get_int`/`get_array`/`get` all answer sane empties). `plan_revisions` does not: the resume and plan-revision code indexes its *last* entry, and an empty list turns that into an `IndexError` inside a hook, which `hookio` converts into a fail-closed denial with no useful message. `STATE_VERSION` makes the migration explicit rather than accidental. `_migrate` runs its arms in order, so a document at version 1 (or missing entirely) reaches the current version in a single pass: the **1→2** arm (`_migrate_1_to_2`) synthesizes revision 0 from the document's own `armed_at` and the plan file as found *right now* — honestly, since no earlier hash was ever recorded to check it against — and a missing, unreadable or symlinked `plan.frozen.md` at that point fails closed as `ARM_FAILED` rather than inventing a plan; the **2→3** arm is a plain `setdefault` of `round_history` and the convergence counters, no evidence recovery needed. Each arm bumps `version` to its own target, never straight to `STATE_VERSION`, so adding a 3→4 arm later is additive. A version this build does not recognise refuses outright, on the same allow-list reasoning `_RESUMABLE` uses elsewhere: a newer build wrote that document, and this one cannot know what its fields mean.

### New state fields

`stop_after_phase`, `resumed_from`, `resumed_into`, `resume_count`, `plan_revisions`, `replan_pending`, `overrides`, `abandoned_pending_tree`, `abandoned_pending_head`, `activation_generation`, `finish_requested`. `STATE_VERSION` 3 adds `round_history`, `transient_failures`, `retry_not_before`, `clarifications` and (phase 3) `clarify_seq`. Several carry an invariant beyond "a new field":

- **`round_history`** is **evidence, not a counter** — it stays out of `resume`'s reset table and is carried forward like the stored reports (get the inverted carry-forward rule right when touching that table). Only `reviewer.execute` appends, only for a parsed `APPROVED`/`CHANGES_REQUIRED` verdict, and only under the same `expected`/`hooks.activation` fingerprint guard `_store_captured_session` uses — an `OP_FAILURE` or `NEEDS_HUMAN` appends nothing, or phase 5's stall check and phase 6's retry budget double-count. Every field read back out of an entry is untrusted: `round_history[*].tree` reaches a `git diff` argv (phase 8) and `--output=` is a real git option, so it goes through `gitsnap.checked_tree` first, and every git call built from a state-supplied object id gets `--` termination. The same fix covers the pre-existing `target.base`/`_write_diff` path.
- **`stall_rounds`** (config, default `3`, `0` disables) is phase 5's stall detection. **Both of its signals ask only about findings a round still stands behind**: `oscillation.persisting` and `oscillation.reversals` alike drop a finding a later round validly retired before computing anchors, because an explicitly retracted finding is evidence of convergence, not of being stuck (`services.go:180` retracted in round 2 and `services.go:226` raised in round 4 is one fix and one new defect, not a moving target). **That is safe only because the two signals are complementary, and a change must keep them so:** retract properly and it is not a reappearance, but every retraction feeds `supersedes_rounds`, and reversing one file in two separate rounds escalates on its own; drop a finding *silently* and raise it again and `reappeared` still catches it — the case `prompts/reviewer-phase.md` already calls a contract violation. Retiring is never free, so neither signal can be dodged by leaning on the other. `reversals.seqs` stays unfiltered on purpose: it is the evidence line a human reads, where "raised in rounds 1, 2, 3" is true even if two were retracted. An anchor no round still stands behind is dropped entirely, however often it was reversed — nothing blocks on it, so there is no disagreement to escalate. Retirement itself is deliberately unbelieving: it matches the **exact** `file=` value (not the line-stripped anchor), refuses an ordinal that names no earlier round, refuses an ambiguous match against two findings in one file, and is consumptive, so a reversal restated in a later round (`prior-rounds.txt` keeps showing it) counts once. `supersedes_rounds` therefore counts *distinct retiring rounds*, not `SUPERSEDES` lines: two reversals inside one round are two fixes, not a flip-flop. A tampered history can hide a stall this way but never fabricate one, and a hidden stall only means the loop keeps reviewing — an escalation is not an approval, so failing to escalate cannot become one. `reviewer._stall_review` runs inside the *same* `state.transaction()` that reserves `report_seq`, and it is the only chokepoint: both `pretool._gate_commit` and `stop._sweep` call `reviewer.execute`, so a check written into `_gate_commit` alone is bypassed by the Stop sweep entirely — see `docs/edge-cases.md`, "A phase that never converges", for the consequence this has no round cap and what that means. `final`-scope reviews are excluded outright; they are cumulative and reached once, with no phase to stall on. **A pre-invoke check on its own is not enough**: the commit gate and the Stop sweep genuinely can overlap, and a second call for the same label reading `round_history` before the first has appended anything would pass the same check and invoke too — whichever finishes first could then be the approving one, acting on a verdict decided blind to the other's still-running repeated-finding evidence. `active_review` (below) is what actually closes that, by refusing the second call outright rather than letting it invoke and race the first to a verdict.
- **`review_attempts`** is `label -> {"generation", "seq"}`: the newest `report_seq` any review *attempt* of that label reserved, whatever became of it. It exists because `round_history` records only attempts that produced a **parsed verdict** — an attempt that timed out, hit a rate limit, broke its contract or escalated appears here and nowhere else. `reviewer.approval_is_current` requires an approving review to still be the newest attempt, and a check against `round_history` alone let a review approve whose successor had merely *failed*: the failure erased the successor from the evidence, and the approval landed on a label whose latest word was something else. Written in the same locked step as the `report_seq` reservation it mirrors (`reviewer._reserve_round`), read under that same lock by every approval path. Deliberately strict — a transient failure in an overlapping review costs the approving one a retry — because the alternative is approving while the gate cannot say what the newest attempt concluded. Degrades safely like `active_review` (a legacy document simply has none), so it needs no migration arm; a missing entry reads as *not current* and denies. `resume` resets it on both paths.
- **`active_review`** is phase 5's per-`(label, generation)` mutual-exclusion claim — unrelated to `reviewer_session` (which is advisory and never authorizes anything; see that field's own entry below). It is a **dict keyed by label** — `{label: {"generation", "claimed_at", "claim_id"}}`, not a single shared record — precisely because a single record lets an unrelated label's claim (a concurrent `final` review while a `phase1` sweep is still running) silently overwrite another label's still-live entry, defeating mutual exclusion for the label that got clobbered. `reviewer._claim_active_review`/`_release_active_review` reuse `_claim_is_live`'s shape (not its default window — see below) for a different resource: this one genuinely prevents two reviews of the same label from running concurrently, which is what makes the stall check's evidence trustworthy at all — see `_reserve_round`'s docstring for why the claim, the stall check and the `report_seq` reservation all have to be one atomic step. A second, overlapping call finds the slot held and is refused as `OP_FAILURE` (`_ACTIVE_REVIEW_BUSY`) before ever building a bundle — it reaches the caller through the existing "unrecognised verdict" fallthrough in `pretool._review_failed`/`stop.SWEEP_FAILED`, so no new branch is needed in either, exactly like phase 5's `NEEDS_HUMAN` short-circuit needed none. Counting a busy slot against `max_failures` is a known rough edge, left for phase 6's transient-failure budget to do better by. **Its expiry window is not `_reclaim_after`** — that one is sized for the session pointer's own lifetime, released right after the primary invocation, before a cold confirmation ever runs. This slot is held for the *whole* `execute` call, cold confirmation included, so `reviewer._active_review_reclaim_after` covers two full `timeout_sec` windows, not one — reusing the narrower window would let a second call reclaim the slot while the first is still legitimately inside its own cold confirmation, reopening the exact race the slot exists to close. **It is a lease, so two rules follow and both are load-bearing.** Every step under it must be separately bounded — `gitsnap.GIT_TIMEOUT_SEC` on metadata git calls, `reviewer.GIT_DIFF_TIMEOUT_SEC` on the two bundle diffs, `VERIFY_TIMEOUT_SEC` on `verify_cmd` — because an unbounded step lets the lease expire while its owner is still legitimately running, and a second review then reclaims the slot and races the first to a verdict. And the window is the **max** of `execute`'s two stretches (building, then invoking), not their sum, because `_renew_active_review` restarts the clock between them; summing would make the lease grow without bound as either side is configured up, and a crashed review would hold the label hostage for the sum. A renewal that finds the slot already taken is not a reclaim — the call reports the busy condition, invokes nothing, and releases nothing. **The lease is renewed at each point its clock must restart — before the primary invocation and again before the cold confirmation — and ownership is proved again inside `_publish`.** The second renewal is not belt-and-braces: between the two model calls sit the SIGTERM grace a timed-out invocation pays and `_settle_pointer`'s session-list call, so a window sized from the first renewal can expire while its owner is legitimately between them. And renewal only narrows the window; a review genuinely slower than the sum can still have its slot reclaimed, so `_publish` refuses to record a round or store a report once `active_review` no longer holds this run's `claim_id` — `OP_FAILURE`, never the verdict it happened to be holding. **A claim's window is recorded on the claim, not recomputed by whoever reads it.** Both sizings derive from `timeout_sec`, ordinary configuration that can change while a claim is held, so recomputing at observation time lets one process reinterpret another's lease — shrink it and a second review reclaims a slot whose owner is still legitimately running; grow it and an abandoned claim is honoured far past anything real. `_claim_active_review` and `_renew_active_review` write `lease_sec`, `_claim_is_live` honours it, and a value past `_MAX_LEASE_SEC` falls back to the reader's own window so a tampered lease cannot pin a label forever. **`_MAX_LEASE_SEC` is derived from the formula it bounds**, not chosen: `timeout_sec` is clamped to `MAX_TIMEOUT_SEC` (`_timeout_sec`, which every reader goes through), and the ceiling is exactly the largest lease that clamp can produce. A hand-picked constant let a big-but-legal `timeout_sec` compute a *legitimate* lease above it, which then read as tampered and fell back — leaving the claim observer-relative again, the very thing recording it was meant to stop. The session-continuity pointer records its own lease the same way. Degrades safely like `reviewer_session` (a legacy document simply has none), so it needed no `STATE_VERSION` bump — same precedent as `manual_accepts`/`reviewer_session` themselves, neither of which is in the 1→2 migration's `setdefault` list either. `resume` resets it explicitly (both paths), even though the `activation_generation` bump every resume already does makes the claim's own generation check ignore a stale one on its own.
- **`transient_failures`, `retry_not_before`, `clarifications`** are counters — they **are** reset by `resume` (`_build_successor_document`), alongside the other per-run counters.
- **Phase 6's `transient_failures`/`retry_not_before`** pace the one class of `OP_FAILURE` a retry can plausibly fix. `ReviewerFailed` is raised by `invoke` for a timeout *and* for every non-zero exit — `127` (no `opencode` on `PATH`), `126`, a bad `--model`, an expired credential — so `reviewer._classify_op_failure` is an allow-list, not a catch-all: `"transient"` only for `status in _TIMEOUT_STATUSES` or a bounded, anchored rate/usage-limit phrase read from the head of the `.out` file; everything else — including `126`/`127` — is `"operational"` and keeps the ordinary `failures`/`max_failures` budget, no pacing, because retrying faster cannot fix a missing binary. `Review.kind` also covers the two other `OP_FAILURE` shapes for the same reason: `"contract"` (every path through `_fail`/`_classify` inside `parse` — the reviewer ran to completion but its output was not the documented contract) and `"bundle"` (`BundleError`, caught in `execute`) both keep the `failures` budget too; only `"transient"` gets its own counter. `pretool._review_failed` branches on `review.kind`: a `"transient"` failure bumps `transient_failures` against `max_transient_failures` (default `5`) and sets `retry_not_before = now() + min(30 * 2**(n-1), 300)`; every other kind is unchanged from before phase 6. Both budgets, exhausted, still only escalate to `NEEDS_HUMAN` — no path here may end in an approval (Rule 1). `approve()` **and `accept.py`'s `_accept`** clear `transient_failures` and `retry_not_before` alongside `failures=0` — an accept that left either standing would have the very tree it just approved still denied by the backoff check for up to `max_transient_failures`' worth of delay. The busy-slot refusal `_reserve_round` returns when `_claim_active_review` finds the per-label slot already held (`_ACTIVE_REVIEW_BUSY`) is also `"transient"`, not `""` — this is the "known rough edge" phase 5's own entry above forward-references: contention with an overlapping review needs the same "retry shortly, do not spend the ordinary budget" treatment as a rate limit, not a strike against `max_failures`. Both denial messages say "since the last approval", not "in a row" or "consecutive" — accurate, because the two counters are independent and neither resets on the other's occurrence: an operational failure sandwiched between two transient ones does not interrupt the transient count, and vice versa. That is deliberate, not a bug — resetting on interleave would let a phase that alternates between failure kinds retry forever, past either limit alone.

- **A `"contract"` failure gets exactly one repair call, and it can only ever recover a *blocking* verdict.** When the reviewer runs to completion and then writes a block `parse` cannot read — a `severity=P1`, a JSON dump, a reformatted block after the provider compacted its own context — `reviewer._repair_contract` hands the **tail** of that transcript back, session-less, cold, with `prompts/reviewer-repair.md` and exactly two attachments: the bundle's manifest-checked `range.txt` and the fenced tail under `context/NNN-repair.txt`. It re-emits the block; it does not re-review, and it is deliberately given nothing it could form a new opinion from. **The outcome rule is the safety argument and it is asymmetric on purpose: only `CHANGES_REQUIRED` carrying at least one blocking finding is accepted.** A repair that approves, that carries nothing blocking, that breaks the contract itself, that times out or that exits non-zero is discarded and the original `OP_FAILURE kind="contract"` stands — because the input is a *tail*, so blocking findings written above the cut are invisible to it, and "this transcript states nothing blocking" is never evidence that the review found nothing. No approval may originate from a repair, which is also why it needs no cold confirmation. **A `SUPERSEDES` line from a repair fails the contract too** (`Invocation.allow_supersedes=False`, ANDed with `target.is_phase` so it can only ever forbid more): the call sees a truncated tail of one transcript and has no earlier round to reverse, so any reversal it wrote would be invented — and it would not stay inert, because `_record_round` stores it and `oscillation` counts reversals as one of the two signals that escalate a phase to `NEEDS_HUMAN`. A repair could otherwise manufacture a stall out of nothing. A recovered round publishes normally and spends nothing from `failures`. It is bounded by its own `REPAIR_TIMEOUT_SEC` (120s), not `timeout_sec`, and runs only when `reviewer._repair_fits` says the **whole-hook** budget covers it plus `reviewer.settle_margin` for everything after it. That reserve is *derived from the steps it covers, not chosen* — the configured harness's `SessionStrategy.capture_timeout_sec` (the largest of them: `_settle_pointer` capturing a fresh round's session is a full `opencode session list` under the OpenCode harness, and nothing at all under one that pre-assigns its session ids), **both** SIGTERM-to-SIGKILL grace windows the two deadlines pay when they expire (`_kill_group` waits each one out), and a flat `_PUBLISH_BUDGET_SEC` for the transactions, the stored report and the caller's JSON emit. A hand-picked 60 was wrong: a round whose repair timed out and whose listing then timed out too overran it, and the shim killed the hook between the repair and `_publish` — losing exactly the report and the recovered round the reserve exists to protect. Keep it derived. `scripts/arl.sh` passes its own `timeout` value as `ARL_HOOK_DEADLINE_SEC`, `cli._start_clock` stamps it (clamped to the same per-subcommand ceiling, since the environment is not a trust boundary), and `reviewer.remaining_budget` counts down from process entry — a per-call sum would be wrong, because by then the hook may already have paid a bundle build, a `verify_cmd` and a full invocation. Skipping is the safe direction and needs no apology; starting a call the shim then kills loses the round *and* the report. Because a repair follows only a failure and a cold confirmation only an `APPROVED`, the two are mutually exclusive, which is what lets `_invoking_budget` be `max(2 * timeout_sec, timeout_sec + REPAIR_TIMEOUT_SEC)` rather than a sum — keep them exclusive or that lease, and `_MAX_LEASE_SEC` with it, stops being an honest ceiling.

The busy-slot classification above creates a real ordering hazard, closed by three separate, complementary fixes rather than one — each closes a different window, and dropping any one reopens a real gap:

- **`_review_failed`'s transient branch is fingerprint-guarded**, the same `expected`/`hooks.activation` comparison `approve()` uses, inside the same `state.transaction()` that would otherwise bump `transient_failures`. A busy-slot loser decides quickly, but *counts* the failure much later relative to a genuinely concurrent, winning review of the same label — which may by then have approved (`approve()` writes `pending_approved_tree`, which **is** one of `hooks.Activation`'s own fields — a correction to an earlier draft of this note, which claimed the opposite), advanced the phase, or otherwise moved the activation. A mismatch denies this specific attempt without touching the counter at all, so a stale write is refused before it can land, not merely tolerated after.
- **`_check_retry_backoff` still runs only after every free shortcut** — byte-identical tree, an already-approved tree, no content diff, an ignore_globs-only change — never before them, even though the fingerprint guard above closes the busy-slot race at its root. It is not redundant: reverting the working tree back to `last_approved_tree` while an *unrelated* backoff is still active (no race at all, a single serial flow) is a case the fingerprint guard cannot see, because nothing about the activation moved — only the working tree did. Moving this check earlier again would deny that legitimate, no-review-needed commit for the remainder of the backoff.
- **`_advance` (`posttool.py`) resets `transient_failures`/`retry_not_before`**, exactly as it already resets `failures`. This is the ordinary, *non-racy* case: a transient failure earlier in a phase, retried successfully — `approve()` already cleared both at approval time, but a later, independent write (the fingerprint guard above closes the specific busy-slot shape of this; nothing closes every conceivable one) must not have those counters survive into the next phase's own budget.

- **`clarify_seq`** (added by phase 3, still `STATE_VERSION` 3) numbers the `context/<n>-question.txt` files a `clarify` writes. It is **not** a counter — like `report_seq` it is *carried forward* by `resume`, never reset: `context/` is copied into the successor byte for byte, so a reset `clarify_seq` would have the first post-resume clarify overwrite a question file inherited from the predecessor.
- **`activation_generation`** must live on *both* staleness fingerprints — `hooks.Activation` and `completion.Fingerprint` — and be incremented on every resume, same-session included, and on every `accept` (`commands/accept.py`). Both dataclasses document themselves as deliberate equality checks over everything rather than deny-lists, precisely because a missing field fails open; this is that failure, closed. Without it, a same-session resume that revises the plan or overrides the model mid-review leaves an in-flight approval keyed to a reviewer scope that no longer exists — and without `accept`'s own bump, a review already in flight when an accept runs (neither fingerprint includes `approved_trees` or `manual_accepts`) could complete afterwards, see no difference, and act on a decision the accept had already superseded. `reviewer.session_ref`'s continuity pointer rides the same two fingerprints for the identical reason — and, since phase 2 of the harness split, a `harness` field beside them: a session id is only meaningful to the CLI that minted it, so a pointer from another harness (or a legacy one carrying no such field) reads as unusable and costs exactly one fresh review, the same safe direction `generation` and `revisions` already fall in.
- **`replan_pending`** fences every mutation except the one exact `set-phases` command, exactly as `ARMED` does before the first freeze — and is cleared by whichever `set-phases` runs next, the ordinary first freeze included. Without that second clearing, a resume that granted the token before phases were ever frozen leaves it live, and a *later* `set-phases` — issued at any point, mid-implementation — takes the replan branch and rewrites the phase currently being worked on.

### The config overlay's place in the precedence chain

`config.load`'s merge order is defaults < user config < repo config < activation overrides < environment. The overlay — an activation's own `--harness`/`--model`/`--variant`, stored in `overrides` — sits between the repo file and the environment. `harness` is *always* written there by `arm` and `resume`, pinned to `probe_config.as_str("harness")` — what `_check_reviewer` actually probed, never the `--harness` value, which `ARL_HARNESS` can outrank and thereby keep out of the probe entirely. It is pinned because it is the only key that decides which binary must exist, and therefore the only one whose drift voids that check; `model` and `variant` stay unpinned. Because each resume probes the reviewer against the overlay it read *before* taking the lock, a write whose base has moved would store a harness/model pair nothing probed, so `resume._refuse_if_the_overlay_moved` compare-and-swaps on the stored overlay inside both the same-session transaction and `_retire` (before retirement, so a refusal leaves the predecessor live) — the second concurrent resume is refused and retried, never merged: a per-run override beats config files, but `ARL_MODEL` still beats everything, including a run's own override. Only keys already in `config.DEFAULTS` are accepted from the overlay; anything else is dropped, because `overrides` is written into `state.json`, which is not a trust boundary this layer should widen.

### The two atomic writers, and which root each may touch

`atomic.write_private_atomic` is the only writer used under `paths.state_root()`: same-directory `os.replace`, and `private_dir_fd` walks every path component down from `root`, `fchmod`ing each `0700` and the file `0600`. That chmod walk is exactly why it must never be pointed anywhere else — rooting it at the repository would chmod the repository directory itself.

`atomic.write_atomic` exists for the one place this plugin writes inside the repository under review: `config <key> <value> --repo`, an explicit, user-only, already-documented write to `.adversarial-review-loop.json`. Same create-temp-then-`os.replace`, but with no chmod of any parent — and it preserves an existing file's mode across a replace (`os.stat` the destination first, `fchmod` the temp to match) rather than silently widening a config file the user deliberately left at `0600`.

## Interpreter invocation

These are non-obvious and silently reversible: each one reverts to something that looks correct, passes a casual reading, and reopens a hole the port closed.

1. **Never `python3 -m arl`, never a relative path.** Hooks run with the repository under review as `cwd`. `-m` puts `cwd` at `sys.path[0]`, ahead of `PYTHONPATH`, so a repo containing `arl/__main__.py` — or merely `json.py` — executes arbitrary code as the gate. Confirmed by experiment. The only sanctioned invocation is `python3 -I "$PLUGIN_ROOT/scripts/arl-bootstrap.py" "$@"`, an absolute, trusted path.
2. **`-I` is load-bearing, not a style choice.** It implies `-P` (no cwd or script-directory on `sys.path`), `-E` (no `PYTHON*` environment influence, `PYTHONPATH` included) and `-s` (no user site-packages). Because `-P` drops the script directory too, `arl-bootstrap.py` re-derives `sys.path` itself from its own `os.path.abspath(__file__)` — trusted precisely because the shim always passes that path absolute.
3. **`sys.pycache_prefix` is set at runtime, before `arl` is imported.** `-I` makes the interpreter ignore `PYTHONPYCACHEPREFIX` (`sys.pycache_prefix` is `None` under `-I`), and `-B` would keep the tree clean at the cost of the bytecode cache on every hook. The bootstrap instead points `sys.pycache_prefix` at `$XDG_CACHE_HOME/adversarial-review-loop/pycache` after verifying the directory does not overlap the plugin repo, the reviewed repo, or `cwd` (`_cache_dir_is_safe` in `arl-bootstrap.py`). If the directory cannot be created or the check fails, `sys.dont_write_bytecode = True` — never a silent fall-back to writing beside the source.
4. **The shim (`scripts/arl.sh`) never `exec`s a hook subcommand.** For `PreToolUse`, Claude Code treats exit 2 as blocking and *any other* non-zero exit as non-blocking — the tool proceeds. A naive `exec python3 …` fails open on a missing interpreter (exit 127, no output) and on an uncaught exception (exit 1, no output). Instead `arl_hook_run` captures stdout into a shell variable (never a temp file — nothing extra to place outside the reviewed repo), and only forwards it when the process exited exactly `0`.
5. **On any non-zero exit, everything captured is discarded**, and the shim emits that event's own fallback (`arl_hook_fallback`) — never Python's partial output. Appending a fallback after a partial write would yield two concatenated JSON objects, which is not valid JSON, and an unparseable `PreToolUse` response is not a denial. The discriminator is exit status, never empty stdout: `pass` legitimately emits zero bytes and exits 0, and it is the commonest hot-path outcome.
6. **The fallback shape is per-event, not one shape reused everywhere:**

   | Entrypoint | Event | Fallback on shim/interpreter failure |
   | --- | --- | --- |
   | `pretool` | PreToolUse | `permissionDecision: "deny"` |
   | `gate-stop` | Stop | `{"decision":"block","reason":…}` |
   | `confirm-commit` | PostToolUse | `additionalContext` describing the failure — a post-hook cannot deny, the tool call already ran |
   | `posttool-failure` | PostToolUseFailure | nothing at all, matching the entrypoint's own silent behaviour; its only job is clearing a pending approval, and a crash here leaves that pending tree stale rather than granting anything |

   Python mirrors this: an uncaught exception at the top level emits the same fallback for its event, through `hookio`'s `Decided` / `OutputFailure` control-flow exceptions, before exiting 0.
7. **A hung parser must still deny, in two layers.** Inside Python, `cmdshape.py` runs the bashlex parse under a `signal.setitimer` deadline (`PARSE_TIMEOUT_SECONDS`) whose handler raises `CommandShapeTimeout`, which the gate treats as a denial. bashlex is pure Python, so `SIGALRM` is delivered between bytecodes and the parse is genuinely interruptible. Outside Python, the shim runs every hook subcommand under `timeout <N>`, `N` fixed below the timeout Claude Code itself enforces per entrypoint (`skills/implement/SKILL.md`) and only reducible for tests via `ARL_SHIM_TIMEOUT_*`, never raisable past the ceiling (`arl_bounded_timeout`). If the in-process alarm never fires — the interpreter wedged in C — `timeout` returns 124, non-zero, and lands in the same discard-and-fallback path as any other failure.
8. **Every state write is same-directory `os.replace`, never a direct write.** `atomic.py` writes to a temp file in the destination directory and renames over the target only after the full document is serialised and flushed — a failed write leaves the last-good file untouched, unlike the old `jq ... | mv -f`, which could truncate a state file and then unconditionally overwrite good state with the failure. The state root, activation directories, and lockfiles get `0700`; state, pointer and report files get `0600`, applied by comparing-then-`fchmod`/opening with an explicit mode rather than trusting `umask` — including tightening a pre-existing `0755` root left over from before this hardening landed. Mutating paths take an `fcntl.flock` around load → mutate → save, so a `PostToolUse` hook overlapping a user-run `defer` cannot lose an update even though the rename alone only prevents a torn file.

## Hot-path rules

The `PreToolUse` dispatcher runs on **every** tool call, so cost there is multiplied by thousands. Two invariants hold it in place:

- **Read-only tools answer before config or state is loaded.** They are permitted in every state, so `commands/pretool.py` hoists `hooks.tool_is_readonly` above loading config and state. The shell repeated this check inside each denying branch too; those repeats were unreachable and are not reproduced in the port. **If a future state ever needs to deny a read-only tool, remove that hoist first** — and put the per-branch checks back with it, or the deny is unreachable in the other direction.
- **One process per job on the hot path.** Config, state and hook-payload parsing are now in-process `json` calls rather than `jq` subprocesses — that whole axis of process count no longer varies by branch the way it did under Bash. What remains fixed per hook is the shim's own floor: the shebang's `env`, the `bash` shim, the `timeout` wrapper, and `python3` — four processes regardless of branch, plus one more `git rev-parse` when `cwd` is outside the armed worktree. Re-measure with `strace -f -e trace=execve` before and after any change that might add a subprocess here; the README's latency table has the current baseline.

## Working on it

```console
make dev-deps                # install the pinned dev dependencies (once per checkout)
make test                    # full suite; no model is called
make test-unit               # the pytest half only
make test-accept             # tests/selftest.sh only
make test-filter FILTER=stop # one selftest section
make check                   # pre-commit: shellcheck, markdownlint, yamllint, actionlint, ruff, mypy
make dry-run                 # print the exact reviewer command and prompt without invoking it
ARL_HARNESS=opencode make dry-run   # the same, for the other harness
```

`make test` needs pytest, which is pinned in `requirements-dev.txt` and installed by `make dev-deps`;
CI installs from the same file, so a local run and a CI run see the same version. That is a
*development* dependency only — the plugin's own runtime needs nothing beyond `python3`, the
standard library, and the vendored bashlex under `scripts/arl/_vendor/`, and must keep working
straight from a checkout with no install step.

`make test` must pass before any commit. A change to the gate needs a test that **fails on the old code** — a test that only asserts a helper's return value while the end-to-end bypass survives is not a regression test.

`make check` runs fix-capable hooks (markdownlint, prettier, end-of-file-fixer). Check `git status --short` afterwards so a formatter's edits are not mistaken for reviewed input.

### Why the gate does not run under uv

`make test` uses `uv` when it is installed — it resolves `requirements-dev.txt` into a cached environment with no virtualenv to manage, and it works where pip refuses to touch the system interpreter (PEP 668). That is a **developer convenience only**. The gate itself must keep running as `python3 -I "$PLUGIN_ROOT/scripts/arl-bootstrap.py"`, and `uv run` must never appear on the hook path. Two measured reasons, both about the same thing — under a hook, the current directory is the repository under review:

- **`uv run` executes code from the reviewed repository.** In a directory containing a `pyproject.toml` with a `backend-path` build backend, `uv run python -I <trusted bootstrap>` ran that backend *before* the bootstrap started. That is the `python3 -m` exploit reintroduced one level up, and the bootstrap's hardening cannot see it.
- **`.python-version` in the reviewed repository redirects the interpreter.** Even with `--no-project`, a repo shipping `.python-version` made uv download CPython 3.9 (27 MB, over the network, inside a hook) and run the gate on it — below the 3.12 floor.

Closing both needs `uv run --no-project --no-config --python <absolute interpreter>` with `UV_PYTHON_DOWNLOADS=never` — at which point uv contributes nothing except latency, and the latency is not small: 122 ms per invocation against 20 ms for `python3 -I`, on a path that runs on every tool call.

**`make check` only sees files git already knows about.** pre-commit enumerates `git ls-files`, so a brand-new file that has never been added is skipped in silence — ruff, mypy and shellcheck report clean on code they never read, and the first real run is the commit hook, after the change has already been reviewed. Run `git add -N` on every new file (intent-to-add is enough; it needs no staged content) before `make check`, and treat a green run that skipped a new module as no run at all.

### Python conventions

- Python 3.12, standard library only at runtime. `requirements-dev.txt` (pytest and friends) is a *development* dependency; the gate itself must keep working straight from a checkout, with no install step.
- `ruff` (`.ruff.toml`, `line-length = 150`, `target-version = "py312"`) and `mypy` (`mypy.ini`, `strict = True`) must both be clean. Both exclude `scripts/arl/_vendor` — it is kept diffable against upstream bashlex, not reformatted or typed to this repo's standard.
- `mypy --strict`: every function is typed, including its return type. `disallow_untyped_defs` and `check_untyped_defs` are both on, so an untyped helper is a lint failure, not a gap that slips through on an existing function.
- One module per concern, not one process sourcing globals — `hookio.py`, `config.py`, `state.py`, `cmdshape.py`, `gitsnap.py`, `reviewer.py`, `report.py` each own one layer, and `commands/` holds one module per subcommand group. Cross-module state is passed explicitly (a `Config`, a `State`, a `Hook`), never a module-level global mutated by a caller.
- Hook entrypoints unwind through `hookio`'s `Decided` / `OutputFailure` control-flow exceptions (deliberately `BaseException` subclasses, not `Exception` — see the class docstrings in `hookio.py`), not through a shell-style `exit 0` scattered across branches.
- `__all__` is declared on every module that has one, and is the module's actual public surface — an import from outside that list is a sign the boundary is wrong, not that the list needs extending.

### `verify_cmd` runs attacker-authored code inside the gate

`verify_cmd` comes from repository configuration, and `build_bundle` runs it through `bash -lc`. It is the only attacker-controlled code that executes in the gate's own process tree, so it runs with the gate's privileges — including write access to the state root that `pretool` denies every tool call. Two consequences, and neither is optional:

- **Evidence is hashed before it runs and re-checked after** (`_hashed_rows` / `_confirm_evidence_unchanged`). Hashing afterwards lets a `verify_cmd` overwrite `changes.00.diff` with benign bytes and have the manifest certify the substitution: the reviewer approves the benign version while the tree being approved still holds the real change. Any byte that moved is a `BundleError`, never a review.
- **Only `verify.txt` is hashed afterwards**, because it is `verify_cmd`'s own output. It is appended without re-reading anything already sealed; rehashing the sealed rows there would hand back the window that was just closed. The same rule is why `_downgrade_bundle_round` updates one row rather than reissuing the whole manifest — and why it verifies the manifest against the digest the review was issued, and `range.txt` against its recorded row, *before* minting a new digest. It is the only place a new trusted digest is created, so it is the only place a corrupted bundle could be laundered into a blessed one.
- **The process group is killed after a normal exit too** (`run_bounded(reap_group=True)`), not only on timeout: `cmd &` otherwise leaves a child holding state-root write access after `build_bundle` has finished checking. A descendant that calls `setsid` still escapes, so every staged attachment is re-checked immediately before the reviewer is launched (`_confirm_staged_unchanged`). That narrows the window; it does not close it, and `docs/security.md` says so rather than implying otherwise.

### Adding config

New keys go in `config.DEFAULTS`, in `config.from_env`'s key list with the right type branch (a severity label also goes in `config.SEVERITY_KEYS`, which is what `configcmd` validates against), and in the README table. Treat repository config as attacker-controlled: a config change must not be able to execute unreviewed code or silently weaken the active gate.

**`final_review` is a key whose entire purpose is to switch a layer off, so it needs the objection answered rather than dodged.** It is admissible because of what it cannot reach: it disables a *backstop* that runs only after every phase has passed the per-commit gate, it can never approve anything (the skip path completes an activation, it does not review one), it does not touch `confirm-commit`, the deny-list or `pretool`, and `finish` ignores it outright. Note "passed the gate", not "was reviewed" — an already-approved or `ignore_globs`-matched tree passes without a model call, so the backstop was never standing behind a guarantee that every line had been read. What it does cost is real and is recorded in the plan and in `docs/security.md`: the cross-phase view, and the second of the two layers above.

Repository config may set it, like every other key, and that is deliberate rather than an oversight. A repository config can already set `ignore_globs: ["**"]` — a strictly worse and complete bypass of *every* per-commit review (`gitsnap.all_paths_ignored`, documented in `docs/security.md`, exercised in `selftest.sh`). Special-casing `final_review` while that stays open would be theatre. If you want to close this class, close it at `ignore_globs` first; a new key is not where the exposure lives.

**`review_guide` (default unset) is the first key whose *value* becomes instruction to the reviewer**, and that difference is what has to be argued rather than waved through. Every other repository-authored input reaches the reviewer as evidence *about* the change, and the prompt says so; a guide is spliced into the prompt itself. It is admissible on the same footing `final_review` is: this layer can already set `ignore_globs: ["**"]`, a complete and strictly worse bypass of every per-commit review, and `verify_cmd` already runs repository-authored code through `bash -lc` inside the gate. Guidance text is the weaker primitive of the three. It is bounded rather than trusted, and the bounds are structural, not stylistic: gate-authored framing that says the guide may not change the contract, the rubric, what blocks or the verdict — and that an attempt to must be reported as a `high` finding against the guide file; splicing *above* the output contract so the contract keeps the last position; a per-composition nonce on the fence so guide text cannot close it; an allowlist (not an escape set) on the one piece of repository text that lands outside the fence, the guide's own path; arm-time refusal of a guide carrying either contract marker, on top of `parse`'s existing exactly-one-block rule; and a verdict recomputed from the `FINDING` lines, so a coerced `VERDICT APPROVED` beside a blocking finding still blocks. What is pinned is the *content*, not the name: `arm` freezes it as `guide.frozen.md` and hashes it, every bundle build re-verifies it, and a copy that no longer matches escalates to `NEEDS_HUMAN` rather than composing a review without it (Rule 1). `resume --guide` records a new revision beside the old one and never overwrites, so `range.txt` can tell a final review that earlier phases ran under different guidance. What none of that prevents is a guide steering *attention* — a bad guide makes reviews worse. That one is disclosed rather than fixed, on every surface a human reads a review from, and it is why the guide and its sha256 are named in the banners, `/status`, stored reports, `range.txt` and `dry-run`.

**`late_block_severity` (default `high`) is the third, and it narrows *what blocks*, so it has to be stated at its real width.** From the second recorded round of a phase on (`reviewer.late_scope`; the policy round is the count of validated `round_history` entries for the label at this generation, *never* the session counter, which resets when continuity drops and advances for rounds that recorded nothing), an actionable finding at or above `block_severity` blocks only if its raw `file=` value — exact first, then with a trailing `:line` stripped — is in the paths changed since the previous round's tree (`gitsnap.changed_paths_strict`, both sides of a rename), or in any earlier round's `file=` values (`prior_files`), or its severity reaches `late_block_severity`; `file=-` is always in scope. Everything else lands in `Review.deferred`, is shown on every approval path (`pretool` approval text, the Stop sweep's next response via `_Gate.deferred`), and is recorded in `round_history` like any other finding — which is the whole semantics: **deferred means "did not block this approval"; the next review of the same phase finds the path in `prior_files` and blocks.** No second approval store exists for it, deliberately. **Every doubt disables the scope, none narrows it** (Rule 1 in the only direction it can point here): round 1, a `final` review, a previous tree that fails `checked_tree`, or *any* entry for the label whose `seq`/`tree`/`verdict`/`findings` does not validate field by field means `scope=None` and the ordinary rule — `_prior_rounds_section` drops a bad line for display, but here a dropped line is a missing path and a missing path *authorises* a deferral. A changed-path listing that fails, or names a path no `FINDING` could spell (`|`, newline, edge whitespace), raises `BundleError` → `OP_FAILURE kind=bundle`. `late_threshold_rank` clamps the key up to `block_severity`, so it can defer but never widen, and an unrecognised label ranks at the floor and is clamped the same way. Stricter-wins is untouched: a reviewer that says `CHANGES_REQUIRED` over a deferred-only set still blocks, and the report shows the deferred lines under their own heading so the disagreement is legible. **It interacts with `cold_confirm`, and the interaction is load-bearing:** deferral is the first state in which a review returns `APPROVED` while *holding* lines at or above `block_severity`, so a cold confirmation replacing the whole `Review` silently dropped them — nothing showed them, `round_history` recorded none, and the next round did not know the path, so the one-approval deferral repeated forever. `reviewer._carry_forward` folds the warm round's `all_findings`/`deferred`/`supersedes` into the cold review that replaces it (deduplicated, and never a line the cold call blocks on), because **a confirmation replaces the verdict, not the record**. The blocking set is deliberately not merged — a warm `APPROVED` has none by construction, and merging one without recomputing the verdict would contradict it — and an `OP_FAILURE` cold call is left alone, since its finding fields are empty on purpose and it records no round. `supersedes` is merged for symmetry: carrying a round's findings forward without its retractions would fabricate a stall out of a history that had none, which is the one direction the stall detector is documented never to fail in.

**`cold_confirm` (default `false`) is the second such key, and it needs its objection answered without overstating the answer.** What it switches off is a *second read of the same gate-generated bundle*, never a review: the round it would re-check ran on evidence built entirely from git, and turning the key off does not touch `block_severity`, the contract parse, `confirm-commit`, the deny-list or `pretool`, and cannot make an operational failure into an approval. **Do not, however, justify it by describing only `prior-rounds.txt`.** That attachment really is narrow — the gate's own rendering of `FINDING` lines it validated with `_FINDING_RE` before storing and re-validates before rendering, type-checked field by field, bounded by `max_findings`/`max_findings_bytes`, inlined through `-f` from outside the invocation's permission allow-list. The *other* channel is not: a continued session (`-s`) carries the whole earlier conversation — previous rounds' attachments, the repository content inside those diffs, the reviewer's own prose — which the gate never re-reads, never bounds, and cannot inspect once the provider compacts it. With the key off, an approving verdict may have been shaped by all of that. An earlier draft of this paragraph claimed the validated attachment was the only model-influenced input; it was wrong, and it contradicted `docs/security.md`'s own injection-persistence note four paragraphs further down. What actually backs the default is the rest of the stack — contract parse, `block_severity`, the deny-list, `confirm-commit`, `approval_is_current`, and the label-keyed session reset that confines one poisoned session to one phase — plus the measured price of the alternative: over a real 45-round run, 11 rounds paid a full, uncached second model call, every one of those cold calls raised new medium findings the warm round had not, and both manual `accept`s in the run followed such an override.

**`max_session_rounds` (default `3`, `0` unlimited) is the one key here that only ever removes context.** `reviewer.session_ref` drops continuity once the stored pointer's `round` reaches it, before the strategy's verify — there is no point paying `SessionStrategy.capture_timeout_sec` to verify a session this call will not continue. It is not a gate-weakening key in either direction: a fresh session carries strictly *less* model-influenced input into the review, and nothing the cap discards is actually lost, because the round-to-round memory the loop depends on is `prior-rounds.txt` and `incremental.diff` — gate-rendered, validated, size-bounded — not the conversation. What it buys is the compaction failure it removes: two of the real run's contract failures (a JSON block for the markers, a `severity=P1 location=` line) landed immediately after OpenCode dumped an `## Objective / Work State` summary into a long session, each costing a whole round and a `failures` slot. **`round` is read through `_pointer_round`, not `_as_int`, in both readers**: it is arithmetic on both sides of the cap (`session_ref` compares it, `_try_claim` adds one to it), so a raw `round: -1000000` out of `state.json` sits below every cap *and* increments back to a negative — one edited integer keeping a session, and the compaction-prone context the cap exists to shed, alive for a million rounds. Clamped at 0 it folds into the case an unparseable or missing `round` already lands in. Clamping only the cap check would leave `_try_claim` writing the negative straight back for the next round to read. **The other thing the check must keep doing is honouring a live claim**: it returns early past `_try_claim`, so it re-runs `_claim_is_live` itself and returns `capturable=False` when another review holds the pointer — a fresh-and-capturable ref there would let `capture_session` overwrite a pointer someone else is mid-conversation with, which is the corruption the claim exists to prevent, arriving through the one path that does not take the claim.

A change that re-couples the two — making the cold path unconditional again, or making its absence widen what a warm verdict may authorise — has to answer that measurement, not just restate the invariant. And keep the two directions of the argument together in `docs/security.md`, per channel rather than averaged: a reader deciding whether to turn the key on needs the guarantee, the thing the default gives up, and the observed price on the same page.

### Adding a harness

A new reviewer CLI is a new module under `scripts/arl/harness/` plus one line in
`harness._registry`. Nothing else in the gate learns its name — that is the property the seam
exists to keep, and the tests below are what stop it eroding.

**A harness composes a command; it never decides anything.** It answers with a `Command`
(argv, env *overrides*, optional stdin, optional cwd) and a `SessionStrategy`, and
`reviewer.py` runs it. Nothing in `harness/` may read a verdict, touch `state.json`, or turn a
failure into an approval. The two places that look like exceptions are not: `transcript()`
*refuses* a run whose own report says a tool was denied or a turn failed — refusing is always
allowed — and `probe_models()` answers `None` for a CLI with no model-list subcommand, which
makes the callers check binary presence only rather than inventing a list.

What a new module has to settle, in the order the existing two settled it:

1. **How the prompt and attachments are delivered.** Both current harnesses inline every
   attachment: OpenCode through `-f`, Claude Code by concatenating them into the payload it
   writes to stdin. That is not a style choice — it is what keeps `context/` from existing at
   a path the reviewer can re-open, which is the whole cold-approval argument in
   `docs/security.md`. A path-based channel is measurably *worse* on tokens as well (the
   benchmark is in the harness split plan), so a third harness that wants one owes both
   arguments. If it inlines, it must verify each attachment's digest as it reads it
   (`Attachment` carries one for exactly this) and raise `PayloadError` on a mismatch — the
   gate's launch-time re-check ends at a pathname and cannot cover bytes this process reads.
2. **How its sessions come into existence.** `DiscoveredSessions` (list-and-match a unique
   title afterwards) and `AssignedSessions` (mint a uuid up front) are the two shapes so far.
   `capture_timeout_sec` must be honest: the gate sizes its claim leases and its
   repair-budget reserve from it, and `_MAX_LEASE_SEC` is the ceiling across *all* registered
   harnesses, so an inflated value there loosens a check for everyone.
3. **What isolation its CLI actually gives, measured rather than read off the flag help.**
   `tests/STEP0.md` records what each probe found; three of the four things the Claude Code
   harness relies on were not what the help implied. Split the flags the way that module does:
   what makes the reviewer read-only is unconditional, and only the *ambient instruction*
   isolation is what `pure` selects.

Then: `tests/unit/test_harness.py` is parametrised over the registry and will pick the new
module up for free (protocol, binary-first argv, no session on a cold or clarify call,
`is_session_id` strictness, the lease ceiling); add a `test_harness_<name>.py` for its own argv
and output shapes, and a `--harness <name>` dry-run block in `tests/selftest.sh`. `make
dry-run` prints whatever `review_command` composed, generically, so there is no rendering to
add — if the new harness's argv looks right there and its stdin carries every attachment
between its fences, the seam is wired.

### The install cache, and what it means for iterating

A local marketplace install **copies** the plugin to `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, but sets `${CLAUDE_PLUGIN_ROOT}` to the `installLocation` — this repository. The two are served from different places:

| What changed | Takes effect |
| --- | --- |
| anything under `scripts/` | **immediately** — hooks run `${CLAUDE_PLUGIN_ROOT}/scripts/arl.sh`, which is the working tree |
| `skills/*/SKILL.md` body or frontmatter | only after the cache is refreshed |
| `prompts/*.md` | immediately, for the same reason as `scripts/` |

`/plugin marketplace update` refreshes the marketplace record but **not** the cached copy when the version is unchanged. To pick up a skill-body change, bump `version` in `.claude-plugin/plugin.json`, then reinstall and restart. A stale body is easy to misdiagnose because the script it invokes is current — the giveaway is an error quoting a command line you no longer have in the repo.

## Host integration

Some behaviour cannot be tested from a shell — skill-hook registration, `` !`…` `` expansion inside a skill body, `${CLAUDE_SESSION_ID}` equality with the hooks' `session_id`, the Stop-hook block cap. These live in `tests/STEP0.md` with an expected result and a fallback each. **Do not claim shell tests cover them**, and do not change the arming path or the skill frontmatter without re-running the relevant STEP0 item.

## Known environment hazards

- `--pure` removes OpenCode **plugins**, not global skills (`~/.config/opencode/skills`) or a global `~/.config/opencode/AGENTS.md`. Both still reach the reviewer; the fixed prompts tell it to ignore ambient style directives and not to invoke a skill for the review. A reformatted review fails the contract, which blocks — it never approves.
- Anything that writes into the worktree between the gate and the commit (an editor writing back a buffer, an MCP server dropping a state directory, a file watcher) changes the tree out from under the approval and lands you in `RECONCILE`. Gitignore such paths before arming.
