# `verify_cmd` runs attacker-authored code inside the gate

The long form of the `verify_cmd` invariants in [`AGENTS.md`](../../AGENTS.md): the hashing order that keeps a bundle honest, and the process-group reap that bounds what it leaves behind.

`verify_cmd` comes from repository configuration, and `build_bundle` runs it through `bash -lc`. It is the only attacker-controlled code that executes in the gate's own process tree, so it runs with the gate's privileges — including write access to the state root that `pretool` denies every tool call. Two consequences, and neither is optional:

- **Evidence is hashed before it runs and re-checked after** (`_hashed_rows` / `_confirm_evidence_unchanged`). Hashing afterwards lets a `verify_cmd` overwrite `changes.00.diff` with benign bytes and have the manifest certify the substitution: the reviewer approves the benign version while the tree being approved still holds the real change. Any byte that moved is a `BundleError`, never a review.
- **Only `verify.txt` is hashed afterwards**, because it is `verify_cmd`'s own output. It is appended without re-reading anything already sealed; rehashing the sealed rows there would hand back the window that was just closed. The same rule is why `_downgrade_bundle_round` updates one row rather than reissuing the whole manifest — and why it verifies the manifest against the digest the review was issued, and `range.txt` against its recorded row, *before* minting a new digest. It is the only place a new trusted digest is created, so it is the only place a corrupted bundle could be laundered into a blessed one.
- **The process group is killed after a normal exit too** (`run_bounded(reap_group=True)`), not only on timeout: `cmd &` otherwise leaves a child holding state-root write access after `build_bundle` has finished checking. A descendant that calls `setsid` still escapes, so every staged attachment is re-checked immediately before the reviewer is launched (`_confirm_staged_unchanged`). That narrows the window; it does not close it, and `docs/security.md` says so rather than implying otherwise.
