# Rule 0: a gate that cannot prove it is running denies

The long form of Rule 0 in [`AGENTS.md`](../../AGENTS.md): why the hooks register at plugin load, and the three things that still deny when a hook call carries no session pointer.

**A gate that cannot prove it is running denies.** The hooks register at plugin load (`hooks/hooks.json`), not on skill invocation, so the dispatcher runs in every Claude Code process the plugin is enabled in — including a fresh `claude --resume` of a session that armed the loop yesterday. Skill-scoped hooks were the original design and they had a hole exactly there: a resumed process registers no skill hooks, `state.json` still says `ACTIVE`, and every commit lands ungated (measured 2026-08-30, see `tests/STEP0.md`). A session pointer binds a session to its activation; a hook call with no pointer is a session that never *completed* `implement`/`resume`. Three things still deny there, checked in this order. (a) The session **asked**: `commands/intent.py` runs on `UserPromptSubmit` and records a marker when the prompt *is* an arming command, before the skill expands — because a failed expansion gives Claude no turn, so nothing the skill body says ever reaches it. `intent` mints a token and `pointer_write` publishes the pointer **carrying that token** before best-effort unlinking, so the check is the token, not the file: a marker the pointer names is answered (a crash between the two leaves litter, not a wedge), while unlinking first would have opened a window with no marker, no pointer and no `latest` in which a saved `ACTIVE` activation went ungated. **The marker's write order is not guaranteed** — measured live, it can land *after* the expansion it announces has already run — so a marker whose worktree has a live gating activation (`ACTIVE`/`ARMED`/`RECONCILE`) bound to the same session is also answered (`hooks._answered_by_live_activation`), never recorded as a failure: the gate is on in both possible histories. An *unanswered* marker means no `arm` has answered since — which is why `hooks.pending_intent` is checked *ahead of* the pointer (a `DISARMED`/`COMPLETE` pointer from an earlier activation must not hide a failed re-arm) and scoped to the worktree the marker names (a failed arm in repository A is neither enforced against nor consumed by a call in repository B). Then `hooks.record_unstarted_arm` records `ARM_FAILED` and denies, exactly as the skill-hook design did. (b) The repository this call is about **cannot be resolved**: `paths.repo_root_or_raise` distinguishes git answering "not a repository" from git not being runnable, a vanished `cwd`, a timeout — the first is a pass, the rest deny, because "nothing to enforce" has to be proven. This holds for *bound* sessions too: `hooks.resolve_repo` raises on the same conditions, and `pretool` denies, `gate-stop` blocks and `confirm-commit` reports "NOT confirmed" rather than reading "could not tell" as "another repository" — which, from a subdirectory of the armed worktree with git off the hook's PATH, would pass a commit run through `/usr/bin/git`. The marker read is three-state for the same reason: absent is "no intent"; unreadable, unscopable or token-less is neither — it denies **everywhere** without being recorded against, or consumed by, whatever repository the call is in, and only `deactivate --session` (the user's `/adversarial-review-loop:stop`) discards it. Consuming it locally would hand repository A's request to repository B and leave A ungated. (c) The worktree's `latest` activation is **still live**: this session is *unbound*, and `hooks.unbound_activation` denies every mutation until `resume` binds it, without touching the other session's document. Everything else — every unrelated session in every unarmed repository — passes silently and writes nothing. Absence of state is never an opt-out; absence of *this session's* state in an armed worktree, or after an arming prompt, is a denial. This is why `deactivate` leaves the session pointer in place and relies on `DISARMED` instead of deleting it.
