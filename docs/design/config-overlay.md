# The config overlay's place in the precedence chain

The long form of the configuration-precedence invariant in [`AGENTS.md`](../../AGENTS.md).

`config.load`'s merge order is defaults < user config < repo config < activation overrides < environment. The overlay — an activation's own `--harness`/`--model`/`--variant`, stored in `overrides` — sits between the repo file and the environment. `harness` is *always* written there by `arm` and `resume`, pinned to `probe_config.as_str("harness")` — what `_check_reviewer` actually probed, never the `--harness` value, which `ARL_HARNESS` can outrank and thereby keep out of the probe entirely. It is pinned because it is the only key that decides which binary must exist, and therefore the only one whose drift voids that check; `model` and `variant` stay unpinned. Because each resume probes the reviewer against the overlay it read *before* taking the lock, a write whose base has moved would store a harness/model pair nothing probed, so `resume._refuse_if_the_overlay_moved` compare-and-swaps on the stored overlay inside both the same-session transaction and `_retire` (before retirement, so a refusal leaves the predecessor live) — the second concurrent resume is refused and retried, never merged: a per-run override beats config files, but `ARL_MODEL` still beats everything, including a run's own override. Only keys already in `config.DEFAULTS` are accepted from the overlay; anything else is dropped, because `overrides` is written into `state.json`, which is not a trust boundary this layer should widen.
