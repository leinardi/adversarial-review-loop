# State fields, migrations, and what may be trusted out of `state.json`

The long form of the state invariants in [`AGENTS.md`](../../AGENTS.md): why `state.json` is not a trust boundary, what `STATE_VERSION` migrations may and may not synthesize, and the invariant each added field carries.

## `state.json` is not a trust boundary — treat everything read out of it that way

This applies to every field this feature added. A `plan_revisions[*].file` is a filename read out of state and then used to open a file: validate it with `paths.is_safe_component`, resolve it under the activation directory with `os.path.realpath` on both sides (a symlink planted in the activation directory must not redirect the read), and verify its recorded `sha256` before its content is used for anything — including showing it to the reviewer. A missing file, a failed containment check, or a hash mismatch is `NEEDS_HUMAN`, never a skipped attachment and never a silent fallback to `plan.frozen.md`. The same caution applies to `resumed_into`, `abandoned_pending_tree` and `abandoned_pending_head`: read for display or comparison, never trusted on their own to authorize a write.

## `STATE_VERSION` and legacy activations

Activations written before this feature exist on disk with none of the fields it needs — and they are exactly the ones a user wants to resume. Most missing fields degrade safely on their own (`State.get_int`/`get_array`/`get` all answer sane empties). `plan_revisions` does not: the resume and plan-revision code indexes its *last* entry, and an empty list turns that into an `IndexError` inside a hook, which `hookio` converts into a fail-closed denial with no useful message. `STATE_VERSION` makes the migration explicit rather than accidental. `_migrate` runs its arms in order, so a document at version 1 (or missing entirely) reaches the current version in a single pass: the **1→2** arm (`_migrate_1_to_2`) synthesizes revision 0 from the document's own `armed_at` and the plan file as found *right now* — honestly, since no earlier hash was ever recorded to check it against — and a missing, unreadable or symlinked `plan.frozen.md` at that point fails closed as `ARM_FAILED` rather than inventing a plan; the **2→3** arm is a plain `setdefault` of `round_history` and the convergence counters, no evidence recovery needed. Each arm bumps `version` to its own target, never straight to `STATE_VERSION`, so adding a 3→4 arm later is additive. A version this build does not recognise refuses outright, on the same allow-list reasoning `_RESUMABLE` uses elsewhere: a newer build wrote that document, and this one cannot know what its fields mean.

**The 4→5 arm is the one that is not a `setdefault`, and it is the reason the bump exists at all.** `manual_accepts`, `reviewer_session`, `active_review` and `review_attempts` were all allowed to arrive without a bump, because a missing value simply read as an empty default. `ended_capture`'s **absence is a signal**, not a default: it is what tells a document that ended *before* the end-state record existed (silence — there is nothing to report, and current HEAD answers a different question) apart from one whose `status` was edited straight into `state.json`, which is the documented Rule 4 bypass that leaves no command to inspect. Without a bump those two are the same bytes and the second is silent. So the arm resolves the ambiguity from the **stored status**, at the one moment the question still has an answer: already terminal → leave the fields absent, exactly as the 3→4 arm declines to synthesize a guide revision 0, because inventing evidence is worse than refusing; not terminal (live, or `ARM_FAILED`/`NEEDS_HUMAN`, for which no writer records evidence) → give it the current schema's empty record, so a later hand-edited status is *present and empty* and gets reported.

**`_migrate` only runs inside `transaction()`, which is why `pretool._upgrade_stale_document` exists.** Both hooks read without one, so an un-migrated document stays un-migrated for as long as nothing writes to it — and a legacy activation that is still live would keep the absent record, handing the state-edit bypass its silence. `pretool` runs the pending migration once, on the first tool call it gates; the wrapper has to make at least one, and every one arrives there first. One write per activation ever, a dict lookup thereafter, and **deliberately not hoisted above `hooks.tool_is_readonly`**, so the read-only hot path is unchanged. It does mean a legacy activation with no `plan.frozen.md` reaches its `ARM_FAILED` escalation on the next tool call rather than the next write — earlier, and in the denying direction. What remains open, and is documented rather than implied: a status edited by something that never passes a hook at all, which is the user's own shell and not the threat model.

## New state fields

`stop_after_phase`, `resumed_from`, `resumed_into`, `resume_count`, `plan_revisions`, `replan_pending`, `overrides`, `abandoned_pending_tree`, `abandoned_pending_head`, `activation_generation`, `finish_requested`. `STATE_VERSION` 3 adds `round_history`, `transient_failures`, `retry_not_before`, `clarifications` and (phase 3) `clarify_seq`. Several carry an invariant beyond "a new field"

`STATE_VERSION` 4 adds `guide_path` and `guide_revisions`. **`STATE_VERSION` 5 adds `ended_capture`, `ended_head`, `ended_tree` and `ended_at`** — what the gate could see at the moment enforcement stopped, written only inside a terminal transition and write-once, the first one winning. `ended_capture` is the discriminator rather than `ended_at`, because a freshly armed document already carries `ended_at: 0`; it holds exactly one of `"recorded"`, `"unborn"` or `"unreadable"`, so a capture that *failed* stays reportable instead of degrading into "nothing to see". `hooks.end_state` validates the **raw** document rather than the coercing accessors — `get_int` maps every malformed value to `0` and `int(True) == 1` slips through it — and uses `gitsnap.looks_like_object_id`, **not** `checked_tree`: a genuinely recorded tree legitimately stops resolving after a rewrite, reset or gc, and letting that turn a true report into silence is the one direction Rule 1 forbids. The shape check suffices because the value never reaches argv. All four are in both resume reset tables (the inverted carry-forward rule: a successor is live, so it has not ended).

Several carry an invariant beyond "a new field":

- **`round_history`** is **evidence, not a counter** — it stays out of `resume`'s reset table and is carried forward like the stored reports (get the inverted carry-forward rule right when touching that table). Only `reviewer.execute` appends, only for a parsed `APPROVED`/`CHANGES_REQUIRED` verdict, and only under the same `expected`/`hooks.activation` fingerprint guard `_store_captured_session` uses — an `OP_FAILURE` or `NEEDS_HUMAN` appends nothing, or phase 5's stall check and phase 6's retry budget double-count. Every field read back out of an entry is untrusted: `round_history[*].tree` reaches a `git diff` argv (phase 8) and `--output=` is a real git option, so it goes through `gitsnap.checked_tree` first, and every git call built from a state-supplied object id gets `--` termination. The same fix covers the pre-existing `target.base`/`_write_diff` path.
- **`stall_rounds`** (config, default `3`, `0` disables) is phase 5's stall detection. **Both of its signals ask only about findings a round still stands behind**: `oscillation.persisting` and `oscillation.reversals` alike drop a finding a later round validly retired before computing anchors, because an explicitly retracted finding is evidence of convergence, not of being stuck (`services.go:180` retracted in round 2 and `services.go:226` raised in round 4 is one fix and one new defect, not a moving target). **That is safe only because the two signals are complementary, and a change must keep them so:** retract properly and it is not a reappearance, but every retraction feeds `supersedes_rounds`, and reversing one file in two separate rounds escalates on its own; drop a finding *silently* and raise it again and `reappeared` still catches it — the case `prompts/reviewer-phase.md` already calls a contract violation. Retiring is never free, so neither signal can be dodged by leaning on the other. `reversals.seqs` stays unfiltered on purpose: it is the evidence line a human reads, where "raised in rounds 1, 2, 3" is true even if two were retracted. An anchor no round still stands behind is dropped entirely, however often it was reversed — nothing blocks on it, so there is no disagreement to escalate. Retirement itself is deliberately unbelieving: it matches the **exact** `file=` value (not the line-stripped anchor), refuses an ordinal that names no earlier round, refuses an ambiguous match against two findings in one file, and is consumptive, so a reversal restated in a later round (`prior-rounds.txt` keeps showing it) counts once. `supersedes_rounds` therefore counts *distinct retiring rounds*, not `SUPERSEDES` lines: two reversals inside one round are two fixes, not a flip-flop. A tampered history can hide a stall this way but never fabricate one, and a hidden stall only means the loop keeps reviewing — an escalation is not an approval, so failing to escalate cannot become one. `reviewer._stall_review` runs inside the *same* `state.transaction()` that reserves `report_seq`, and it is the only chokepoint: both `pretool._gate_commit` and `stop._sweep` call `reviewer.execute`, so a check written into `_gate_commit` alone is bypassed by the Stop sweep entirely — see `docs/edge-cases.md`, "A phase that never converges", for the consequence this has no round cap and what that means. `final`-scope reviews are excluded outright; they are cumulative and reached once, with no phase to stall on. **A pre-invoke check on its own is not enough**: the commit gate and the Stop sweep genuinely can overlap, and a second call for the same label reading `round_history` before the first has appended anything would pass the same check and invoke too — whichever finishes first could then be the approving one, acting on a verdict decided blind to the other's still-running repeated-finding evidence. `active_review` (below) is what actually closes that, by refusing the second call outright rather than letting it invoke and race the first to a verdict.
- **`review_attempts`** is `label -> {"generation", "seq"}`: the newest `report_seq` any review *attempt* of that label reserved, whatever became of it. It exists because `round_history` records only attempts that produced a **parsed verdict** — an attempt that timed out, hit a rate limit, broke its contract or escalated appears here and nowhere else. `reviewer.approval_is_current` requires an approving review to still be the newest attempt, and a check against `round_history` alone let a review approve whose successor had merely *failed*: the failure erased the successor from the evidence, and the approval landed on a label whose latest word was something else. Written in the same locked step as the `report_seq` reservation it mirrors (`reviewer._reserve_round`), read under that same lock by every approval path. Deliberately strict — a transient failure in an overlapping review costs the approving one a retry — because the alternative is approving while the gate cannot say what the newest attempt concluded. Degrades safely like `active_review` (a legacy document simply has none), so it needs no migration arm; a missing entry reads as *not current* and denies. `resume` resets it on both paths.
- **`active_review`** is phase 5's per-`(label, generation)` mutual-exclusion claim — unrelated to `reviewer_session` (which is advisory and never authorizes anything; see that field's own entry below). It is a **dict keyed by label** — `{label: {"generation", "claimed_at", "claim_id"}}`, not a single shared record — precisely because a single record lets an unrelated label's claim (a concurrent `final` review while a `phase1` sweep is still running) silently overwrite another label's still-live entry, defeating mutual exclusion for the label that got clobbered. `reviewer._claim_active_review`/`_release_active_review` reuse `_claim_is_live`'s shape (not its default window — see below) for a different resource: this one genuinely prevents two reviews of the same label from running concurrently, which is what makes the stall check's evidence trustworthy at all — see `_reserve_round`'s docstring for why the claim, the stall check and the `report_seq` reservation all have to be one atomic step. A second, overlapping call finds the slot held and is refused as `OP_FAILURE` (`_ACTIVE_REVIEW_BUSY`) before ever building a bundle — it reaches the caller through the existing "unrecognised verdict" fallthrough in `pretool._review_failed`/`stop.SWEEP_FAILED`, so no new branch is needed in either, exactly like phase 5's `NEEDS_HUMAN` short-circuit needed none. **A busy slot spends neither budget** (`Review.contended`): not `failures`, because a different reviewer command or model is not what a retry needs, and not `max_transient_failures`, because no call was made to earn a place in it -- the slot is checked before anything is invoked. That distinction is not bookkeeping. Nothing releases the claim of a hook the host killed mid-review, and an interrupted turn is enough to do it, so the claim then stands for the rest of its lease -- up to 32 minutes under the default `timeout_sec`. Counting those denials hands one crashed hook the power to walk an activation it is not part of to `NEEDS_HUMAN` on a wall clock nothing in the repository can affect. Denying is still the answer; escalating is not, and the denial is paced (`pretool._CONTENDED_BACKOFF_SEC`) so a live holder is not hammered either. **The denial names the remaining lease and the way out**, because "wait for it to finish" is unactionable advice when the holder does not exist: `_claim_remaining_sec` supplies the same number the check enforces, and the recovery is a resume, whose `activation_generation` bump makes the claim's own generation check ignore it immediately. Without both, a reader reaches for the activation's `lock` file -- the state mutex, which holds none of this and must not be deleted. **Its expiry window is not `_reclaim_after`** — that one is sized for the session pointer's own lifetime, released right after the primary invocation, before a contract repair ever runs. This slot is held for the *whole* `execute` call, contract repair included, so `reviewer._active_review_reclaim_after` covers `timeout_sec + REPAIR_TIMEOUT_SEC`, not `timeout_sec` alone — reusing the narrower window would let a second call reclaim the slot while the first is still legitimately inside its own repair, reopening the exact race the slot exists to close. **It is a lease, so two rules follow and both are load-bearing.** Every step under it must be separately bounded — `gitsnap.GIT_TIMEOUT_SEC` on metadata git calls, `reviewer.GIT_DIFF_TIMEOUT_SEC` on the two bundle diffs, `VERIFY_TIMEOUT_SEC` on `verify_cmd` — because an unbounded step lets the lease expire while its owner is still legitimately running, and a second review then reclaims the slot and races the first to a verdict. And the window is the **max** of `execute`'s two stretches (building, then invoking), not their sum, because `_renew_active_review` restarts the clock between them; summing would make the lease grow without bound as either side is configured up, and a crashed review would hold the label hostage for the sum. A renewal that finds the slot already taken is not a reclaim — the call reports the busy condition, invokes nothing, and releases nothing. **The lease is renewed at each point its clock must restart — before the primary invocation and again before the contract repair — and ownership is proved again inside `_publish`.** The second renewal is not belt-and-braces: between the two model calls sit the SIGTERM grace a timed-out invocation pays and `_settle_pointer`'s session-list call, so a window sized from the first renewal can expire while its owner is legitimately between them. And renewal only narrows the window; a review genuinely slower than the sum can still have its slot reclaimed, so `_publish` refuses to record a round or store a report once `active_review` no longer holds this run's `claim_id` — `OP_FAILURE`, never the verdict it happened to be holding. **A claim's window is recorded on the claim, not recomputed by whoever reads it.** Both sizings derive from `timeout_sec`, ordinary configuration that can change while a claim is held, so recomputing at observation time lets one process reinterpret another's lease — shrink it and a second review reclaims a slot whose owner is still legitimately running; grow it and an abandoned claim is honoured far past anything real. `_claim_active_review` and `_renew_active_review` write `lease_sec`, `_claim_is_live` honours it, and a value past `_MAX_LEASE_SEC` falls back to the reader's own window so a tampered lease cannot pin a label forever. **`_MAX_LEASE_SEC` is derived from the formula it bounds**, not chosen: `timeout_sec` is clamped to `MAX_TIMEOUT_SEC` (`_timeout_sec`, which every reader goes through), and the ceiling is exactly the largest lease that clamp can produce. A hand-picked constant let a big-but-legal `timeout_sec` compute a *legitimate* lease above it, which then read as tampered and fell back — leaving the claim observer-relative again, the very thing recording it was meant to stop. The session-continuity pointer records its own lease the same way. Degrades safely like `reviewer_session` (a legacy document simply has none), so it needed no `STATE_VERSION` bump — same precedent as `manual_accepts`/`reviewer_session` themselves, neither of which is in the 1→2 migration's `setdefault` list either. `resume` resets it explicitly (both paths), even though the `activation_generation` bump every resume already does makes the claim's own generation check ignore a stale one on its own.
- **`transient_failures`, `retry_not_before`, `clarifications`** are counters — they **are** reset by `resume` (`_build_successor_document`), alongside the other per-run counters.
- **Phase 6's `transient_failures`/`retry_not_before`** pace the one class of `OP_FAILURE` a retry can plausibly fix. `ReviewerFailed` is raised by `invoke` for a timeout *and* for every non-zero exit — `127` (no `opencode` on `PATH`), `126`, a bad `--model`, an expired credential — so `reviewer._classify_op_failure` is an allow-list, not a catch-all: `"transient"` only for `status in _TIMEOUT_STATUSES` or a bounded, anchored rate/usage-limit phrase read from the head of the `.out` file; everything else — including `126`/`127` — is `"operational"` and keeps the ordinary `failures`/`max_failures` budget, no pacing, because retrying faster cannot fix a missing binary. `Review.kind` also covers the two other `OP_FAILURE` shapes for the same reason: `"contract"` (every path through `_fail`/`_classify` inside `parse` — the reviewer ran to completion but its output was not the documented contract) and `"bundle"` (`BundleError`, caught in `execute`) both keep the `failures` budget too; only `"transient"` gets its own counter. `pretool._review_failed` branches on `review.kind`: a `"transient"` failure bumps `transient_failures` against `max_transient_failures` (default `5`) and sets `retry_not_before = now() + min(30 * 2**(n-1), 300)`; every other kind is unchanged from before phase 6. Both budgets, exhausted, still only escalate to `NEEDS_HUMAN` — no path here may end in an approval (Rule 1). `approve()` **and `accept.py`'s `_accept`** clear `transient_failures` and `retry_not_before` alongside `failures=0` — an accept that left either standing would have the very tree it just approved still denied by the backoff check for up to `max_transient_failures`' worth of delay. The busy-slot refusal `_reserve_round` returns when `_claim_active_review` finds the per-label slot already held (`_ACTIVE_REVIEW_BUSY`) is `"transient"` for the pacing and `contended` for the accounting: it is denied and paced like a rate limit, and counted like neither budget, for the reason `active_review`'s own entry above gives. Both denial messages say "since the last approval", not "in a row" or "consecutive" — accurate, because the two counters are independent and neither resets on the other's occurrence: an operational failure sandwiched between two transient ones does not interrupt the transient count, and vice versa. That is deliberate, not a bug — resetting on interleave would let a phase that alternates between failure kinds retry forever, past either limit alone.

- **A `"contract"` failure gets exactly one repair call, and it can only ever recover a *blocking* verdict.** When the reviewer runs to completion and then writes a block `parse` cannot read — a `severity=P1`, a JSON dump, a reformatted block after the provider compacted its own context — `reviewer._repair_contract` hands the **tail** of that transcript back, session-less, cold, with `prompts/reviewer-repair.md` and exactly two attachments: the bundle's manifest-checked `range.txt` and the fenced tail under `context/NNN-repair.txt`. It re-emits the block; it does not re-review, and it is deliberately given nothing it could form a new opinion from. **The outcome rule is the safety argument and it is asymmetric on purpose: only `CHANGES_REQUIRED` carrying at least one blocking finding is accepted.** A repair that approves, that carries nothing blocking, that breaks the contract itself, that times out or that exits non-zero is discarded and the original `OP_FAILURE kind="contract"` stands — because the input is a *tail*, so blocking findings written above the cut are invisible to it, and "this transcript states nothing blocking" is never evidence that the review found nothing. No approval may originate from a repair. **A `SUPERSEDES` line from a repair fails the contract too** (`Invocation.allow_supersedes=False`, ANDed with `target.is_phase` so it can only ever forbid more): the call sees a truncated tail of one transcript and has no earlier round to reverse, so any reversal it wrote would be invented — and it would not stay inert, because `_record_round` stores it and `oscillation` counts reversals as one of the two signals that escalate a phase to `NEEDS_HUMAN`. A repair could otherwise manufacture a stall out of nothing. A recovered round publishes normally and spends nothing from `failures`. It is bounded by its own `REPAIR_TIMEOUT_SEC` (120s), not `timeout_sec`, and runs only when `reviewer._repair_fits` says the **whole-hook** budget covers it plus `reviewer.settle_margin` for everything after it. That reserve is *derived from the steps it covers, not chosen* — the configured harness's `SessionStrategy.capture_timeout_sec` (the largest of them: `_settle_pointer` capturing a fresh round's session is a full `opencode session list` under the OpenCode harness, and nothing at all under one that pre-assigns its session ids), **both** SIGTERM-to-SIGKILL grace windows the two deadlines pay when they expire (`_kill_group` waits each one out), and a flat `_PUBLISH_BUDGET_SEC` for the transactions, the stored report and the caller's JSON emit. A hand-picked 60 was wrong: a round whose repair timed out and whose listing then timed out too overran it, and the shim killed the hook between the repair and `_publish` — losing exactly the report and the recovered round the reserve exists to protect. Keep it derived. `scripts/arl.sh` passes its own `timeout` value as `ARL_HOOK_DEADLINE_SEC`, `cli._start_clock` stamps it (clamped to the same per-subcommand ceiling, since the environment is not a trust boundary), and `reviewer.remaining_budget` counts down from process entry — a per-call sum would be wrong, because by then the hook may already have paid a bundle build, a `verify_cmd` and a full invocation. Skipping is the safe direction and needs no apology; starting a call the shim then kills loses the round *and* the report. The repair is the **only** call that can follow the primary invocation under the lease, which is what lets `_invoking_budget` be exactly `timeout_sec + REPAIR_TIMEOUT_SEC` — a second call added there without widening it makes that lease, and `_MAX_LEASE_SEC` with it, stop being an honest ceiling.

The busy-slot classification above creates a real ordering hazard, closed by three separate, complementary fixes rather than one — each closes a different window, and dropping any one reopens a real gap:

- **`_review_failed`'s transient branch is fingerprint-guarded**, the same `expected`/`hooks.activation` comparison `approve()` uses, inside the same `state.transaction()` that would otherwise bump `transient_failures`. A busy-slot loser decides quickly, but *counts* the failure much later relative to a genuinely concurrent, winning review of the same label — which may by then have approved (`approve()` writes `pending_approved_tree`, which **is** one of `hooks.Activation`'s own fields — a correction to an earlier draft of this note, which claimed the opposite), advanced the phase, or otherwise moved the activation. A mismatch denies this specific attempt without touching the counter at all, so a stale write is refused before it can land, not merely tolerated after.
- **`_check_retry_backoff` still runs only after every free shortcut** — byte-identical tree, an already-approved tree, no content diff, an ignore_globs-only change — never before them, even though the fingerprint guard above closes the busy-slot race at its root. It is not redundant: reverting the working tree back to `last_approved_tree` while an *unrelated* backoff is still active (no race at all, a single serial flow) is a case the fingerprint guard cannot see, because nothing about the activation moved — only the working tree did. Moving this check earlier again would deny that legitimate, no-review-needed commit for the remainder of the backoff.
- **`_advance` (`posttool.py`) resets `transient_failures`/`retry_not_before`**, exactly as it already resets `failures`. This is the ordinary, *non-racy* case: a transient failure earlier in a phase, retried successfully — `approve()` already cleared both at approval time, but a later, independent write (the fingerprint guard above closes the specific busy-slot shape of this; nothing closes every conceivable one) must not have those counters survive into the next phase's own budget.

- **`clarify_seq`** (added by phase 3, still `STATE_VERSION` 3) numbers the `context/<n>-question.txt` files a `clarify` writes. It is **not** a counter — like `report_seq` it is *carried forward* by `resume`, never reset: `context/` is copied into the successor byte for byte, so a reset `clarify_seq` would have the first post-resume clarify overwrite a question file inherited from the predecessor.
- **`activation_generation`** must live on *both* staleness fingerprints — `hooks.Activation` and `completion.Fingerprint` — and be incremented on every resume, same-session included, and on every `accept` (`commands/accept.py`). Both dataclasses document themselves as deliberate equality checks over everything rather than deny-lists, precisely because a missing field fails open; this is that failure, closed. Without it, a same-session resume that revises the plan or overrides the model mid-review leaves an in-flight approval keyed to a reviewer scope that no longer exists — and without `accept`'s own bump, a review already in flight when an accept runs (neither fingerprint includes `approved_trees` or `manual_accepts`) could complete afterwards, see no difference, and act on a decision the accept had already superseded. `reviewer.session_ref`'s continuity pointer rides the same two fingerprints for the identical reason — and, since phase 2 of the harness split, a `harness` field beside them: a session id is only meaningful to the CLI that minted it, so a pointer from another harness (or a legacy one carrying no such field) reads as unusable and costs exactly one fresh review, the same safe direction `generation` and `revisions` already fall in.
- **`replan_pending`** fences every mutation except the one exact `set-phases` command, exactly as `ARMED` does before the first freeze — and is cleared by whichever `set-phases` runs next, the ordinary first freeze included. Without that second clearing, a resume that granted the token before phases were ever frozen leaves it live, and a *later* `set-phases` — issued at any point, mid-implementation — takes the replan branch and rewrites the phase currently being worked on.
