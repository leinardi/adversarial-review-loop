# Resume, retirement, and one live activation per worktree

The long form of the resume invariants in [`AGENTS.md`](../../AGENTS.md): the retire-first order, what a retirement may never span, what a retired directory may never become, and the inverted carry-forward rule.

## Resume: a second arming path

`resume` continues an existing activation rather than starting one — across a new session (the ordinary case) or in the current one (to change `--until`, the model, or the plan without a new session). It shares helpers with `arm.py` (`_ArmFailure`, `_resolve_plan`, `_check_reviewer`, the flag parser) but lives in its own module, `commands/resume.py`, because the invariants below are specific to it.

**Neither `skills/implement/SKILL.md` nor `skills/resume/SKILL.md` carries a `hooks:` block, and neither may grow one.** Every hook lives in `hooks/hooks.json` and registers at plugin load — see "Plugin-level hooks, 2026-08-30" in `tests/STEP0.md`. Skill hooks register on invocation, per process, and were the reason a resumed session could commit ungated while `state.json` claimed enforcement; adding one back would also fire the gate twice per tool call in the process that invoked the skill. If a skill ever needs an extra hook, it goes into `hooks/hooks.json` for every session.

### One live activation per worktree

Two activations gating the same worktree independently — each with its own pointer, each approving commits against its own approval set — is the failure every rule below exists to rule out.

**Cross-session resume retires the predecessor before the successor exists, never the reverse.** Retirement writes `status: "RESUMED"` under the predecessor's own lock; only after that succeeds is the successor's directory materialised, its document written, and the pointers repointed. This is the fail-closed order: if the process dies in between, the predecessor is `RESUMED` (denying) and the successor has no state at all (denying, per Rule 0) — both sides deny, **there is no automatic rollback**, and the recovery is `implement`. The reverse order — successor first, predecessor retired second — would leave a real window with two simultaneously `ACTIVE` activations over one worktree.

**A retirement must never span an in-flight approval.** `pretool` sets `pending_approved_tree` under the same lock a retirement takes, so the two serialise: whichever wins, the other observes a consistent world. Skip this and a `pretool` approval can land against the predecessor moments before it is retired, and `confirm-commit` then verifies that commit against the now-retired document. `_advance`'s `status="ACTIVE"` write is what makes this dangerous rather than merely stale: it would resurrect a blocking `RESUMED` activation back into a second live one. `_advance` is kept off `RESUMED` documents two ways — `_REPORT_ONLY` rather than `_RECONCILABLE` keeps `posttool._reconcile` off it, and retirement itself refuses to happen across a pending approval — because a `status="ACTIVE"` write from *any* code path is the resurrection mechanism, not just this one, and both guards exist for exactly that reason.

**A retired activation's directory is never mutated — with one bounded exception.** Every later revision, every later report is written into the *successor's* directory, copied byte for byte from the predecessor at retirement time. Editing anything in a retired directory would corrupt evidence a completed review was already run against, and reports already stored there still name it. The exception: a `reviewer.execute` **already in flight** when retirement lands. A review holds no lock across its (minutes-long) run by design, so `build_bundle` and `invoke` may already have written `bundles/<seq>/` and `raw/<seq>-*` into what is now the retired directory, and those cannot be unwound. Everything `execute` still controls at that point *is* withheld: the `state.json` fingerprint guard (`hooks.Activation`, checked under the lock in every no-write path), and `_publish` writing the stored report **and** the `round_history` entry inside one such guarded transaction — one publication, so a retirement lands wholly before it (neither is written) or wholly after it (the successor copies both), never between the two. The stranded `bundles/`/`raw/` files are this-review-only and additive — no successor code path ever reads them, since the successor rebuilds its own bundle — so they are litter, not corruption. Closing even that needs retirement to fence in-flight reviews (there is no signal one is running today); it is a change to the retirement path, not to `execute`. A `clarify` in flight is the same shape: it may strand a `context/<n>-question.txt` and a `raw/<n>-clarify.out`, and it withholds the reply itself — its post-invoke `hooks.Activation` recheck refuses `_MOVED_DURING_RUN` rather than printing a clarification the activation no longer owns.

**The `ended_*` record is part of the retiring transaction, and it is write-once.** Each of the three terminal transitions folds `hooks.ended_evidence` into the same `state.update` as its status write — one code path, so the evidence can never land without the transition or the transition without the evidence, and no caller may substitute a tree it already holds (deriving the tree from the captured commit is what keeps the pair self-coherent). `ended_evidence` catches every `GitUnavailable` and records it as an outcome; a raise inside the caller's transaction would abandon a completion over a reporting field. Retirement is the one that needs a rule rather than a call: it captures **only when the predecessor's stored status was still live** (`!= "DISARMED"`), decided from the status and never from whether a record is already there. Enforcement in a stopped activation ended at the `deactivate`, and re-capturing at retirement would record today's ungated HEAD and have the retired session accuse work the user was entitled to do after stopping. A truthiness test is wrong twice over — a legacy `DISARMED` document has no `ended_capture` at all, and a corrupt one is evidence `end_state` reports as malformed. The write happens after `copy.deepcopy(prev_state.data)`, so the retirement's own evidence never reaches the successor, which resets the four fields anyway.

**`.git/info/exclude` is the one ignore file the gate can neither see past nor review, so its digest is baselined at arm.** `gitsnap.snapshot` stages with `git add -A`, which obeys that file — and it lives *outside* the worktree, so no commit carries it and no review ever sees it. One line written there turns a file really sitting in the worktree into a clean worktree: measured, a staged `backdoor.py` went from `?? backdoor.py` to `worktree_clean = True` with the snapshot tree falling back to the baseline. That defeats the dirty check and the turn-end sweep at once, which is precisely the guarantee `confirm-commit` prints ("the turn-end sweep still covers anything left uncommitted"). It cannot get unreviewed code into history — an excluded path is never staged, so it never enters a commit's tree — but it can leave work in the repository the gate called clean, and a stated guarantee that is false in a reachable case is the thing to fix. **The fix is not to look through the file.** Ignored paths are what it exists for, and sweeping `node_modules` into a review would make every turn end unusable; `.gitignore` needs no equivalent because it is inside the repository and a change to it is itself reviewed. `arm` records `gitsnap.exclude_digest` and `stop._exclude_moved` compares, blocking with the file's real path (`--git-path`, never a hand-built `.git/info/exclude` — a linked worktree's `.git` is a file, and guessing would answer `EXCLUDE_ABSENT` forever, a digest that never changes and therefore a check that never fires). **Three things are not a change, each for its own reason.** An empty baseline is an activation armed before the field existed — calling that a change would block every document already on disk, the permanent-alarm failure the end-state record exists to avoid, reintroduced one field over. **Only an absent baseline is allowed to pass**, and the comparison is tri-state rather than boolean, because "it changed", "the baseline is not one an arm wrote" and "the current state could not be read" are three different claims and only the first is evidence about the worktree. A `""` *reading* blocks as unverifiable with its own message: `exclude_digest` answers that for a `rev-parse` that failed or timed out — and `git_run` reports an expiry as status 124, a denial everywhere else — so passing on it lets one transient failure complete an activation under ignore rules nothing compared. The sandbox argument that once justified passing does not survive the order things run in: `_review` blocks on `SnapshotError` before any of this is reached, so git has already answered by the time the guard runs, and a repository that genuinely cannot be read never gets there. And `resume` deliberately leaves the field out of both reset tables, so the successor inherits the predecessor's baseline: naming it would re-baseline at every resume, and one `/adversarial-review-loop:resume` would launder an edit made under the predecessor into the successor's starting truth. **Absence and present-empty are different, and collapsing them is how this check turns itself off.** Absent is a document written before the field existed: silence. Present-and-empty cannot be produced by any current `arm` — it refuses rather than store a baseline it could not establish, exactly as it already refuses when it cannot establish whether the worktree is clean — so an empty one means an edited document, and it blocks. Reading it as legacy would let one unreadable moment during arming disable the check for the life of the activation, silently, on the worktrees least able to prove anything: the same `_ABSENT`-sentinel lesson as `ended_capture`, one field over. **The digest is captured before the cleanliness check and re-verified immediately before the document is written**, so the "this worktree is clean" verdict and the recorded baseline describe one and the same set of ignore rules; a writer adding an exclusion and the file it hides in the window between them (the plan freeze, the reviewer probe, the guide freeze all sit there) would otherwise have the arm activate over work already hidden. **And the Stop gate re-checks after every reviewer call, not only once up front** — a review is a minutes-long window in which the worktree keeps moving, and an exclude edit landing mid-sweep hides whatever was created beside it, leaving the cleanliness check that follows to read the worktree as clean and complete the activation. The field needs no migration arm — a document that predates it degrades exactly as `active_review` does.

**`deactivate` no longer rewrites a document that already ended.** `commands.resolve_local_activation()` filters on loadability, never on status, so `/adversarial-review-loop:stop` used to overwrite a `COMPLETE` or `DISARMED` document unconditionally — measured, discarding which of the two actually ended the mode. With the record in place that is worse than untidy: re-running `/stop` is the obvious remedy for a report the user disagrees with, and it would stamp today's unapproved HEAD in as the evidence. The guard abandons the transaction through a local `_AlreadyEnded`, mirroring `stop._Terminal`, because `transaction()`'s exit saves unconditionally and a plain `return` would resave a retired document. `RESUMED` is the exception, and it is not a no-op at all. Reaching that branch **proves the resume died mid-publication**: resolution reads `latest`, so a resume that got as far as repointing would have resolved the successor and never landed there. The message it replaced offered "run `/stop` again now that this worktree's pointer names it", which is unreachable by construction — the pointer never moves on its own, so the user re-ran `/stop` against identical text forever while the worktree stayed gated. `_finish_the_retirement` instead reads the successor `resumed_into` already committed to under the predecessor's own lock, stops it if it is live, and publishes the pointer the dead resume did not. That is not inventing a transition: it converges on the value retirement decided and the resume was on its way to writing. Three outcomes, three messages — successor live (stopped), successor already terminal (pointer finished, neither document touched), successor never published (`/stop` genuinely cannot free this worktree, and says so; `implement` is the recovery). The walk follows chained retirements with a visited set *and* a hard cap, since `state.json` is not a trust boundary and a self-naming `resumed_into` must terminate rather than spin. **Every link is checked in both directions before it is followed**, and that check is load-bearing rather than tidy: what the walk authorises is a status write and a `latest` publication against whatever the field names, so an edited `resumed_into` in a retired document would otherwise aim `/stop` at an unrelated *live* activation — disarming it and publishing it as this worktree's — a strictly wider escape than the state edit it rides in on. Retirement writes the pair together (`resumed_into` on the predecessor, `resumed_from` on the successor), so a half-present link was not written by this gate and is refused. **The pointer write belongs inside the successor's own transaction**, because `resume`'s `_retire` runs inside that same document's `transaction()`: published after the lock released, a concurrent resume could retire the successor and repoint `latest` at *its* successor, and this call would then overwrite that pointer with a session now `RESUMED` — wedging the worktree while reporting it freed. A successor found `RESUMED` under the lock is never published at all; the walk simply runs again, bounded, because a chain still growing under this command is a resume storm rather than a state to converge on. **That lock is necessary and not sufficient, and the gap is worth stating rather than papering over:** `latest` has five publishers — `arm` twice, `resume`, `hooks` and this — and none of them serialise against each other, so the successor's lock orders this against a resume *of that successor* and nothing else. A concurrent `implement` can arm and publish an unrelated activation mid-repair, and overwriting that pointer would leave `latest` on a stopped session while a live one gates every unbound session resolving through it — fail-open, the one direction this codebase never accepts. So publication is conditional on `latest` still naming the activation the repair was resolved from, checked before the pointer write *and* before the transaction saves, so a refusal changes nothing at all. It is a compare-and-swap without an atomic swap; closing the residual window means putting every `latest` write behind one worktree-scoped lock, which is a change to `arm` and `resume`. **What the message may claim is narrower than what the pointer says.** `pretool`, `gate-stop` and `confirm-commit` resolve a *bound* session's own document before they look at the pointer, so every session bound to a retired activation keeps denying and keeps reporting from that retired document however the pointer is repaired — and in a chained A-into-B-into-C history that is every retired link, not just the one this command resolved. Both published-pointer messages carry that caveat; naming only the resolved activation would describe B's session as free. **The retired document is never written** — the rule above ("a retired activation's directory is never mutated") holds unchanged — and the claim the new message makes is deliberately narrower than "commits are not gated": `pretool` reads the *calling session's* own document, so a session still bound to the retired predecessor keeps being denied whatever the pointer says, and the message says exactly that.

### The inverted carry-forward rule

The successor's document is built by copying the whole predecessor document and then resetting a *named* set of fields — never by enumerating what to keep. Enumerating what to keep is how a future field gets silently dropped the day it is added to `new_state_document` and this reset table is not updated to match. It already has one concrete failure mode on record: an explicit keep-list drops `report_seq`, and `reviewer.py` claims the next sequence from state and `shutil.rmtree`s the bundle directory for that sequence — a reset `report_seq` would have the first post-resume review overwrite the copied `001` report and destroy its bundle rather than continuing the sequence.
